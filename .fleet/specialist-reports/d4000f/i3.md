### Exactly where and how I gate the write path — quoted

u2's primitive is deliberately unauthenticated and states so: *"Every caller must gate before
calling. There is no gate inside."* I inherit that obligation. The gate is the route's export:

```ts
// src/app/api/ingest/plan/route.ts:51
export const POST = withAgentRoute(INGEST_WRITE, async ({ db, request }) => {
```

`withAgentRoute` supplies, in this order, before my handler body runs at all: **FR-4** bearer
token verified; **FR-5** capability asserted and `ctx.db` scoped by `agentScopedDb` so the handler
cannot reach `contract_milestone`; **FR-8** rate limit enforced; **FR-6/FR-59** exactly one
`audit_log` row per outcome including refusals. `ctx.db` is the scoped client and is the only one
I pass down — I never call `createServiceClient()`.

The two modules beneath the route (`plan-document.ts`, `mark-collisions.ts`) also carry no gate,
by the same reasoning u2 gives, and both say so in their docstrings. Both carry
`import "server-only"`, so a Client Component reaching them is a build error rather than a runtime
surprise.

**Capability choice:** `ingest:write` reused rather than a new member minted. It grants **no new
authority** — a token holding it can already insert `work_item` rows through `POST
/api/ingest/run`, and this route writes the same table under the same §7a class. A new capability
would need a new stored-enum member, i.e. a migration. **Queued anyway (Q5), because it is a
capability boundary.**

## Security posture applied

Only `work_item` is touched, and only through u2's primitive.

| Table | Class | Source | At rest | Retention | Deletion path |
|---|---|---|---|---|---|
| `work_item` | sensitive | **spec §7a** | `description` pgcrypto via `encrypt_field` (u2's primitive); `plan_ref` deliberately CLEAR | §7a Q3 baseline: indefinite — unchanged | unchanged; M1.10 export-and-purge owns it |
| `engagement` | personal | **spec §7a** | read-only here (slug → id) | unchanged | n/a |

`plan_ref` clear beside an encrypted `description` is §7a's own stated pattern for `requirement`
(`text` encrypted, `ref` and `section` clear), and Phase 1 decision 3: *encrypting the
reconciliation key would delete the requirement it exists for.* An encrypted column cannot be
indexed or matched, and this one is an upsert conflict target.

Controls from §7a: **4** (work_item class and its two encrypted columns; the clear-key exception;
agent capability scoping; no `contract_milestone` reach) · from baseline: **3** (request body size
cap, bounded `in (...)` chunk, no database mechanism in an error message) · **NOT VERIFIED: 4** —
listed under Verification with what would settle each.

Unclassified tables I refused to guess at: **none** — every table this unit touches has a §7a row.

- Every error message this unit produces carries **no** Postgres mechanism. A database message

### A §7a defect I introduced and my own test caught

`PlanIngestResult` initially `extends PlanDocumentMapping`, which carries `inputs` — and those
hold the **plaintext** `description`, §7a `sensitive`. The route never echoed `inputs`, so nothing
leaked over the wire, but the *result object* is exactly what ends up in a log line, and u2 omits
`description` from `PlannedWorkRecord` for precisely this reason. Fixed with
`Omit<PlanDocumentMapping, "inputs">` plus destructuring the prose out at the call site. There is
now a test (`returns counts and line numbers, never the plan's prose`) and a mutation (M9) that
re-introduces it and is caught. Recorded as a lesson in `CLAUDE.md`.

## Best-guess decisions

1. **I modified `POST /api/ingest/run` (25 lines) to mark collisions after `persistPlan`.**
   Confidence **med**; the largest thing in this report the orchestrator may want to reverse.
   *Why:* FR-90's trigger is an ingested run meeting a planned row, and that meeting happens in
   either order. Marking only on the plan path leaves a real collision unmarked whenever the run
   lands second, which reads as reconciled. Both call sites use one shared function so they cannot
   disagree about what a collision is. *Blast radius:* `persistPlan` already returned
   `engagementId`, so **`persist.ts` is untouched**; the change is one call plus a `reconciliation`
   block added to the response. The full suite passes, so no existing assertion on that response
   broke. *If reversed:* delete the call and the response block; the plan path stands alone and is
   still correct, just incomplete in one direction.

2. **One extra engagement lookup per plan post.** `ingestPlanDocument` resolves the slug to an id
   itself even though u2's primitive resolves it again internally. Confidence **high**.
   `markPlanCollisions` needs the id even when **zero** rows were written — every task unparsed, or
   every keyed task already present — and in that case there is no returned record to read it off.
   Reaching into u2's private resolver, or skipping the mark when nothing was inserted, would each
   be worse; the second would skip the mark on exactly the repeat post.

3. **`decideCollisions` does not exempt a planned row that carries a `plan_ref`.** Confidence
   **high**. It cannot be keyed to an ingested row inside one engagement anyway — i1's unique index
   on `(engagement_id, plan_ref)` makes a second row with that key impossible, so the upsert skips
   instead. And conservatism points one way: `collision` says "still two rows, not merged", which
   is true regardless. The other direction would claim a reconciliation that did not happen.

4. **I imported `fetchAllRows` from `@/lib/server/releases/db`** rather than re-implementing
   paging. Confidence **med** — it is a generic helper living in a domain package, which is a
   coupling worth noting. Duplicating paging logic is how the 1000-row incident happens twice.

5. **I built a second test double** (`__fixtures__/fakePlannedDb.ts`) rather than extending
   `server/ingest/__fixtures__/fakeDb.ts`. Confidence **high**. The shared one's `eq`/`in` are
   no-ops that return the chain — correct for asserting *what the writer sends*, and useless here,
   where the property under test **is** the filtering. Against a non-filtering double, mutation M4
   (deleting the `unreconciled` filter) would have survived. Mine filters for real and models i1's
   `plan_reconciliation` column default; the docstring states what it still cannot prove.
