## Interface contract — the exact signatures u4 and i3 call

**Module: `@/lib/server/workitems/planned`** (file:
`src/lib/server/workitems/planned.ts`). Pure: no database import, no `new Date()`, no
environment. Safe to import from a server component; it is already imported by three server
modules, and `src/app/work-items/_lib/*` already imports its sibling `workitems/rules`.

```ts
/** FR-91, ruled at Q15. Inclusive: >= this many days untouched is STALE. */
export const PLANNED_STALE_AFTER_DAYS = 30;

/** FR-87's status half of the planned predicate. Value: "pending". */
export const PLANNED_STATUS: StoredWorkStatus;

/**
 * FR-87 — `execution_mode IS NULL AND status = 'pending'`.
 * Takes the RAW work_item columns, snake_case on purpose (see below).
 */
export function isPlannedRow(row: {
  execution_mode: unknown;
  status: unknown;
}): boolean;

/** Whole UTC calendar days between the two, or null if either is unreadable. */
export function daysUntouched(updatedAt: string | null, asOf: string): number | null;

/** The two facts a read path records so the rule can be applied later. */
export interface PlannedItem {
  planned: boolean;
  updatedAt: string | null;
}

export type PlannedStalenessState = "not-planned" | "fresh" | "stale" | "unknown";

export type PlannedStaleness =
  | { state: "not-planned"; daysUntouched: null }
  | { state: "fresh";       daysUntouched: number }
  | { state: "stale";       daysUntouched: number }
  | { state: "unknown";     daysUntouched: null };

/**
 * FR-91. `asOf` is `YYYY-MM-DD` or a full ISO instant — the CALLER's clock,
 * never this function's.
 */
export function plannedStaleness(item: PlannedItem, asOf: string): PlannedStaleness;

/** The planned rows out of a loaded set. */
export function selectPlanned<T extends { planned: boolean }>(items: readonly T[]): T[];
```

**How u4 calls it, end to end:**

```ts
import { plannedStaleness } from "@/lib/server/workitems/planned";

// `item` is a ListedWorkItem | LoadedWorkItem | WorkItemDetail — all three now
// carry `planned` and `updatedAt`.
const staleness = plannedStaleness(item, today);   // today: "2026-08-24"
// staleness.state -> "not-planned" | "fresh" | "stale" | "unknown"
// staleness.daysUntouched -> number for fresh/stale, null otherwise
```

`today` is produced the way every other answer already produces it — `handlers.ts:75`'s
`todayFrom()`, i.e. `(options?.now?.() ?? new Date()).toISOString().slice(0, 10)`. A screen with no
handler options can build the same string itself. **Do not let `plannedStaleness` invent it.**

**The four `state` arms are all object arms with string-literal discriminants**, deliberately —
`string | null | "stale"` collapses to `string | null` and discriminates nothing (fleet learning,
run `eb2490`). They are plain objects, so they cross the RSC boundary intact.

## The design decisions, stated as decisions

### 1. Exactly 30 days is STALE — the boundary is inclusive

The spec says "untouched for 30 days surfaces as STALE" and does not say which side of 30 it falls
on. **Chosen: `daysUntouched >= 30`.** "Untouched for 30 days" is true at thirty days, and a
boundary left to the reader is a boundary two callers implement two ways. Stated once as
`PLANNED_STALE_AFTER_DAYS` and tested at 29 (fresh), 30 (stale) and 31 (stale), plus the literal
pair `2026-07-25` → stale / `2026-07-26` → fresh against `2026-08-24`, spelled out so a change to the
test's own date arithmetic cannot silently move the boundary. Queued as a question; **confidence
high**.

### 2. Whole UTC calendar days, not elapsed instants

`updated_at` is a `timestamptz`; the rule truncates both sides to a UTC calendar day via `toIsoDay`
and differences them with `daysBetween`. **Consequence, stated rather than buried: a row touched at
`23:59Z` and one touched at `00:01Z` on the same date are the same age here**, so a row can surface
STALE up to ~24h "early" against an instant reading. Chosen because it is the arithmetic every other
elapsed count in this product uses (`daysWaiting`, `isOverdue`), because it matches the existing
`today: string` parameter every answer already takes, and because early surfacing is the
conservative direction for a signal that deletes nothing and transitions nothing. Tested explicitly
at `00:00:00.000Z`, `12:00:00Z` and `23:59:59.999Z` on the boundary day, so the truncation is
asserted rather than incidental. Queued; **confidence med**.

### 3. `planned` is read from the raw column, not derived from the domain object

`fromExecutionMode(null)` returns `"fleet"`, so by the time a row is a `LoadedWorkItem` the FR-87
signal is gone. `isPlannedRow` therefore takes the raw `work_item` columns, spelled **snake_case**
so a caller cannot pass a camelCase domain object to it by accident, and each read path records the
answer before the lossy conversion runs.

**This makes i4 independent of D-1 in both directions.** Nothing here needs D-1 fixed, and nothing
here breaks when u4 fixes it. i4 does **not** fix D-1 and did not touch `fromExecutionMode`,
`ExecutionModeChip` or the `executionMode` field on any of the three row types — that remains u4's,
exactly as the manifest assigns it. **`executionMode` still reads `"fleet"` on a planned row after
this unit; `planned` is the field that is true.** No test here asserts the broken behaviour, so
u4's fix will not have to delete one.

### 4. An unreadable timestamp is `unknown`, never `fresh`

`state: "unknown"` is a real arm of the union. Guessing `fresh` hides a row that may have sat for a
year; guessing `stale` cries wolf. `updated_at` is `NOT NULL DEFAULT now()` behind i1's
`BEFORE UPDATE` trigger, so this should be unreachable — which makes it a real finding about a read
path if u4 ever renders it. u4 needs a distinct treatment for it. Queued.

### 5. No DB-level "planned only" filter was added

`WorkItemFilters` gained nothing. The answer screens already load their engagement's rows and
filter in memory (`next.ts`'s `READY_STATUSES`), so `selectPlanned` is the shape that fits, and a
`/work-items` filter chip is u3's screen rather than a filter nobody in this run consumes. The
PostgREST form, for whoever needs it later, is `.is("execution_mode", null).eq("status",
PLANNED_STATUS)`.

### 6. FR-91 changes no ordering and no inclusion rule

A stale planned row still appears in Next, in the same position. FR-91 says "surfaces as STALE" and
Q15 says "surfaced and never deleted"; nothing licenses demoting or excluding it. Queued so c1/u4
do not each decide separately.

## Prior fleet learnings used

- `Knowledge/A TypeScript union of string with a string literal does not discriminate - the sentinel
  arm must not be a string.md` — **CONFIRMED and applied.** The naive `PlannedStaleness` is

  indistinguishable nulls — the exact "absence rendered as a claim" hazard the note names. The union
  here has four object arms with string-literal discriminants and no wide `string` arm; the note's
  point 3 (RSC serializability) is why they are plain objects rather than symbols, and they cross
  the boundary into u4's components intact.
- `Knowledge/Supabase codegen types every returns-table column as non-null and reverts hand
  annotations.md` — **read, and it does NOT explain D-1.** The note is scoped to `returns table
  (...)` functions and says outright that "for ordinary tables the generator is correct".
  `database.types.ts` types `work_item.execution_mode` correctly nullable after i1 regenerated it.
  D-1's root cause is the *next* link in the chain and is not in the vault: **the row interfaces
  these read paths use are hand-written (`WorkItemRow` in `list.ts`) or untyped

  widened generated type reaches nothing and `tsc` stays silent.** Offered as a candidate learning
  for the run's routing step rather than written to the vault by me.
