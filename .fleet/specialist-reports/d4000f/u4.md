### The fix

`fromExecutionMode` now ends `?? EXECUTION_MODE_UNPARSED` instead of `?? "fleet"`,
mirroring `fromWorkStatus` one function above. `EXECUTION_MODE_UNPARSED` is a new
member of the domain `ExecutionMode` union and is **deliberately absent from
`EXECUTION_MODES`**, the ingest wire vocabulary — so `validateWorkItem` refuses it
from an artifact and `toExecutionMode` answers `null` for it, which `ingest/plan.ts`
already counts as an unmappable enum. The sentinel is read-only by construction, not
by comment.

**No information is lost by folding SQL NULL together with an unreadable value.**
FR-87's planned signal is *only* the NULL, and `isPlannedRow` decides it from the raw
column before this conversion; every read path already records the answer as its own
field. That is exactly why i4 built it that way.

### The second half of D-1, found while mapping the blast radius

The brief's table named `chips.tsx:235` as needing its domain type widened. The
underlying cause is one level down and worth recording: **`src/lib/server/workitems/list.ts`
declared `execution_mode` and `executionMode` as non-nullable `StoredExecutionMode`
while the column underneath them is nullable.** That is the hand-written-row-interface
problem the brief described, in its purest form — i1's correctly widened
`database.types.ts` reached nothing, `tsc` stayed silent, and a planned row's raw
`null` flowed to `EXECUTION_MODE_LABELS[null]`, came back `undefined`, and drew the
blank chip. Both are now `| null`.

**`ExecutionModeChip` had no test of its own.** That is why this shipped: the same
B43/B46 shape where a component nothing ever mounts is broken for every reader and
provably fine to every test. It has one now, and so does its wiring into the real table.

### One consistency defect I introduced and then closed

Widening the domain type made the two read paths hand the chip the same row in two
shapes — the listing passes the raw `null`, the domain loaders pass `"unparsed"` — so
`/work-items` and `/work-items/<id>` would have drawn **two different chips for one
row**. Rather than an `if` at each call site, `planned` is now a **required** prop on
`ExecutionModeChip` and the rule lives in the component once. A test asserts the two
shapes produce byte-identical markup.

### i4's comment at `planned.ts:21` — updated, behaviour untouched

It read "`fromExecutionMode(null)` returns `"fleet"`", which is now false. Rewritten to
state the corrected premise and note that **the conclusion is unchanged**: the sentinel
is returned for a NULL and for an unreadable value alike, only the NULL is planned, so
the domain object still cannot answer FR-87's question and `isPlannedRow` still must
read raw columns. **I did not route i4's code through the fixed function.** Comment only.
