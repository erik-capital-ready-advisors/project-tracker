## Key findings requiring routing attention

1. **The resolved spec (`.fleet/resolved-spec-d4000f.md:369`) asserts "Eleven of these screens
   already read `searchParams`". This is false against HEAD `0594209`.** `/runs`
   (`src/app/runs/page.tsx`) and `/registry` (`src/app/registry/page.tsx:34`) take zero props and
   read no `searchParams` today. Only 9 of 11 do. This should be corrected wherever the spec's
   claim gets propagated into Phase 2 unit briefs — the two units touching those screens are
   building new capability, not extending existing capability.
2. Of the 9 that do read `searchParams`, there are **3 divergent implementations**: a shared
   `SearchParams` type + `parse*Query` helpers in `src/lib/answer-query.ts` (6 screens); a
   byte-identical but separately-declared `SearchParams` type in
   `src/app/work-items/_lib/query.ts` (1 screen, no shared parser); and two screens
   (`/questions`, `/waits`) that inline the `Record<string, string | string[] | undefined>` type
   with no shared parser at all. Recommend one shared `engagementFilterFrom()` helper added to
   `answer-query.ts` for FR-96b, adopted by all 11 rather than diverging further.
3. `listEngagements()` (`src/lib/server/registry/engagements.ts:156-168`) does not filter archived
   engagements today — FR-96's "picker lists active engagements only" needs a new query, not reuse
   of the existing one.
4. FR-96c's "explicit no such engagement state" must not be conflated with the existing
   `notFound()` behavior on `/registry/[slug]:136`, which is a different case (bad route param, not
   an unresolvable query filter).
5. No shared StrictMode test-render helper exists in this repo; every fetching-screen test inlines
   `render(<StrictMode>{...}</StrictMode>)`. Confirmed across 18 test files.
