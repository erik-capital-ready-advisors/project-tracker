## The interface i3 consumes

```ts
parsePlanDocument(text: string, engagement: string, source: string): PlanParseResult
```

`PlanParseResult = ParsedPlan | NotAPlan`, discriminated on `kind` with **object** arms — a bare
string-literal sentinel beside a `string` arm does not discriminate (measured, run `eb2490`;
see Prior fleet learnings below).

`ParsedPlan` carries `tasks: PlanTask[]`, `orphanSteps`, `unparsedTasks`, `unparsedSteps`,
`tasksWithPlanRef`, `tasksWithoutPlanRef`.
`PlanTask` carries `id`, `engagement`, `source`, `ordinal`, `line`, `rawHeading`, `taskNumber`,
`planRef`, `title`, `status` (`pending` | `unparsed`), `steps`, `implements`.

**Why not `WorkItem`.** FR-87 requires `execution_mode` unset on a planned row, and
`WorkItem.executionMode` is non-nullable with `validateWorkItem` requiring it present. Widening
that type is i1/i3's call, not a parser's, and doing it here would have touched a type three other
units are building against. `PlanTask` is a plan-document record; mapping it onto a `work_item`
row is the persistence path.

**Naming.** `src/lib/server/ingest/plan.ts` already exists and already exports `PlannedWorkItem`
for an unrelated concept (the persistence plan for a run ingest). This module is therefore
`planDocument.ts` and uses none of those names.

## The two lines Q12 draws, and how each is encoded

| Case | Behaviour | Encoded as |
|---|---|---|
| Document not of the plan shape | Rejected **whole** | `{ kind: "not-a-plan", source, reason }` — three keys, zero rows |
| Line inside a genuine plan it cannot classify | `status: "unparsed"`, source line verbatim | a row in `tasks` / `task.steps` |

`reason` is `no-task-headings` or `no-checkbox-steps`. Recognition requires **both** at least one
well-formed `### Task N: <title>` heading outside a fence **and** at least one well-formed
`- [ ]` / `- [x]` step beneath one, which is the conjunction the ruling states.

There is a test asserting a rejected document hands back literally `["kind","source","reason"]` and
no rows, because the failure to guard against is a manifest producing eight `unparsed` rows that
read on screen as eight unclassified things rather than one file that was never a plan.

## `unparsed` discipline — candidates broad, classification narrow

That direction is the whole rule and it is deliberate:

- **Task candidate:** any heading `#{1,6}` whose text starts with the word `Task` (case-insensitive).
- **Task classification:** exactly `### Task <digits>: <non-empty title>`.
- So `### Task Twelve:`, `### Task 3:`, `## Task 4: x`, `#### Task 5: x`, `### Task 6 — no colon`
  all become rows with `status: "unparsed"`, `taskNumber: null`, `title: null` and `rawHeading`
  verbatim. **Emitted, not omitted, and not guessed.**
- **Step candidate:** any bullet with a bracket of at most one character — `/^[ \t]*[-*+][ \t]+\[(.?)\]/`.
  This deliberately does not match `- [Link](url)`, which is a link bullet and not a checkbox.
- **Step classification:** marker `" "` → `pending`, `"x"`/`"X"` → `done`, anything else →
  `unparsed`. `- [ ]NoSpace` and `- [ ]` with no text are `unparsed` — `- [ ]foo` is not a task
  list item in any markdown dialect, and reading it as `foo` is exactly the guess this refuses.

**Fence awareness is a correctness requirement here, not a nicety.** Measured against `plan.md`:
2 `###` headings (`### 6.1 Access`, `### 6.2 Ingest`) and 4 `##` headings sit inside fenced code as
illustrative content. Without fence tracking they parse as structure. Mutation M3 below proves it.

A non-task heading at level 1–3 ends the task above it, so a checkbox under `## Done when` is an
orphan rather than Task 13's step. Every mid-task `##` in `plan.md` is fenced, so this is safe
against the real artifact; it is measured, not assumed.

## FR-90 — the reconciliation id, honestly reported

- `planRef` is read from a `**Plan-id:** <token>` line in the task body, and is **`null` where
  absent**. Absence is recorded, never filled in.
- `taskNumber` is the positional `N`. It is stored because the artifact says it, and it is
  documented in the type as **never a reconciliation key** — it shifts the moment a task is
  inserted, which is exactly what Q13 rejected.
- **Title and prose are never used.** A test asserts that a document whose tasks all have titles
  still returns `planRef: [null, null]`.
- A `**Plan-id:**` line that cannot be read, or two of them in one task, makes the **task**
  `unparsed` rather than yielding `null`. This is the key that merges rows; ambiguity on it is the
  one place where a quiet `null` would be as dangerous as a guess.
- Against the real `plan.md`: `tasksWithPlanRef: 0`, `tasksWithoutPlanRef: 13`. The corpus test
  asserts that, so when the template starts emitting ids **the test goes red and that is the
  notification**.

The `**Plan-id:**` syntax is a best guess and is queued — see Questions.

### The corpus oracle is independent of the parser

The expected counts in `planDocument.corpus.test.ts` were measured with a line-anchored `awk` pass
over `plan.md` **before** the parser was run against it — a deliberately dumber reader, because a
check figure produced by the code under test checks nothing, and a parser that silently drops rows
raises no error, it returns a smaller and entirely plausible number.

Measured independently, then reproduced by the parser on the first run:

```
13 tasks · 82 steps · per-task [6,7,6,6,6,6,7,6,6,6,6,6,8] · 0 orphans · 0 unparsed
 2 `###` headings inside fences (content, correctly not parsed as structure)
 0 tasks carrying an FR-90 reconciliation id
```

The corpus test **never skips**. `plan.md` is tracked, so a skipped oracle — indistinguishable from
a passing one — cannot happen here; it also asserts `existsSync(PLAN_PATH)` so a removal goes red
rather than quiet. If `plan.md` is later deleted or rewritten, that test fails and the numbers must
be re-measured with the same independent pass, not adjusted to fit.

## Best-guess decisions

1. **`PlanTask`, not `WorkItem`.** Reason above. i3 owns the mapping and the encryption.
2. **`**Plan-id:**` as the id syntax.** Queued as question 1.
3. **Classification candidates are shape-presenting lines only.** Queued as question 2.
4. **One row per `### Task N:` heading.** Queued as question 3.
5. **A malformed or duplicated plan-id makes the task `unparsed`.** Chosen because this is the
   reconciliation key: a wrong one merges two rows that are not the same work, which is precisely
   the wrong `done` CR-005 was written to prevent.
6. **A non-task heading at level 1–3 closes the current task.** Measured safe against `plan.md`,
   where every mid-task `##` is fenced.
7. **`orphanSteps` as its own bucket** rather than a synthetic `unparsed` task. Neither dropped
   (silent omission) nor forced into a task they may not belong to (a guess).
8. **Parser left unwired.** i3 owns the seam. Flagged explicitly because an unwired parser ships
   inert and looks finished.
9. **Tier-2 oracle is `plan.md` in place**, not a byte copy. The brief said "byte-copy fixture";
   the file is already committed at the repo root, so reading it in place *is* the byte copy, at
