## Best-guess decisions

1. **r1's corrections are carried, not silently absorbed.** My brief said "the eleven screens
   already read `searchParams`" — **that is wrong**, and it came from the approved CR's own cost
   claim. Measured: 9 of 11, in 3 shapes; `/runs` and `/registry` read none. The primitive is
   designed to absorb three shapes and bootstrap two screens from nothing, and I rewrote no existing
   parser.
2. **The picker is a GET form with a native `<select>`, not a Radix listbox or a router push.** The
   repo argues this explicitly in `native-select.tsx` and `answer-filter-bar.tsx`: the CSP carries
   `upgrade-insecure-requests` and a browser applying it to a local HTTP origin gets no client
   bundle. Verified working with a native submit.
3. **`EngagementScope` is a Client Component, and it had to be.** A Server Component in the root
   layout receives no `searchParams` and is not re-executed on soft navigation, so anything it
   derived would be right on first load and quietly wrong afterwards. The researcher confirmed
   `useSearchParams()` in a layout-mounted client component is live and SSR-populated on a dynamic
   route; the build confirmed no Suspense boundary is required.
4. **The picker and the badge are one component**, because they read the same fact and two
   boundaries could disagree about whether the screen is filtered — which is the disagreement FR-96a
   exists to prevent.
5. **The slug cap is 128, not `answer-query`'s 200.** 128 is `MAX.slug` in the registry's own
   validator; a longer value cannot name a row. I changed neither existing parser's cap.
6. **No pattern check on the slug.** `?engagement=Acme` resolves to nothing and FR-96c already
   renders that loudly. A second kind of loud for one mistake, plus a copy of the registry's slug
   grammar in the UI layer, is worse.
7. **`page` is the only parameter dropped on a filter change**, matching `withParams` in
   `src/app/work-items/_lib/query.ts` so the shell and that screen cannot disagree.
8. **The eleven paths are written out literally, with a tripwire test** asserting them equal to
   `ALL_ROUTES` minus `/settings/*`. Deriving them would silently enrol the next appended nav entry
   into accepting a parameter it does not honour.
9. **The `roster` prop defaults inline to `{ status: "gated" }`** rather than importing
   `ROSTER_GATED`, so `app-shell.tsx` keeps a **type-only** dependency on the `server-only` module
   and its test does not drag a service-role client into its module graph.
10. **No persistence of any kind.** No cookie, no `localStorage`, no `sessionStorage` — asserted by
    test, per CR-005 §3.3 point 3.
11. **`pnpm gate:m27:e2e` reported NOT VERIFIED rather than run against another tree.** Stated with
    the exact command that settles it.
