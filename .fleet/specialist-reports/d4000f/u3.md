## What each of r1's three `searchParams` shapes cost

r1's correction of CR-005's "eleven of these screens already read `searchParams`" was right, and
the cost was not distributed the way the sentence implies.

| Shape | Screens | What it cost |
|---|---|---|
| shared `SearchParams` + `parse*Query` in `@/lib/answer-query` | 6 | **Cheapest, ~1 file.** One `engagement()` helper replaced six identical `text(params, PARAM.engagement, …)` calls, `PARAM.engagement` became `ENGAGEMENT_PARAM`, and `SearchParams` became an alias of `SearchParamRecord`. No page was touched. These screens already resolved the slug server-side (`engagementUnknown`) and already rendered `UnknownEngagementNotice`, so FR-96c cost **zero**. One real behaviour change fell out and is named below. |
| duplicate-but-identical type in `@/app/work-items/_lib/query` | 1 | **Cheap for the parameter, not for FR-96c.** The parser adoption was the same three edits plus deleting a hand-written `SLUG_LIMIT = 128` that happened to agree with u1's cap. But this screen filtered by slug and had **no way to say a slug named nothing** — a mistyped slug rendered "No work items match these filters.", which is true and is not the answer. Adding the resolution meant restructuring the page's single `loadForOperator` call. |
| ad-hoc inline `Record` on `/questions`, `/waits` | 2 | **Full cost.** Neither had a parser, a rejection channel, an engagement filter, or a filter bar. Each needed: the filter read, a resolution, a new filter argument threaded into its loader (`engagementId` for questions, `engagementSlug` for waits), FR-96c wiring, a scoped empty-state sentence, **and** a fix to its toggle link, which was a literal `"/waits" : "/waits?resolved=1"` pair that would have silently dropped the new filter on the first click. |
| **no `searchParams` at all** — `/runs`, `/registry` | 2 | **Highest.** Everything the two above needed, plus the prop itself and a filter path into the read layer that did not exist. `/runs` needed `listRuns` and the `cache()`d `readRuns` to take an engagement id, plus a stale doc comment retracted (it asserted FR-96 was DRAFT). `/registry` needed a resolution built from the list it already holds. `/runs`' existing test called `RunsPage()` with no arguments and had to be updated. |

**The one behaviour change from adoption.** `answer-query`'s `TEXT_LIMIT` is 200 and is right for
`owner` and `environment`; a slug is capped at 128 by `MAX.slug`. A 129–200 character `engagement`
value used to be accepted, then matched nothing, then reached FR-96c the long way. It is now
reported as the unusable filter value it is. Either way it is loud and no rows are widened, and
for every value that can name a row the six screens behave identically. Pinned by a new case in
`tests/answer-query.test.ts` which also asserts `owner` keeps 200, so the two caps cannot be
collapsed by accident.

## Best-guess decisions

1. **A rejected (over-128) engagement value maps to FR-96c on the four new screens and stays in
   `RejectedFilters` on the seven with a filter bar.** `confidence: med`, queued. The trap avoided:
   `engagementFilterSlug()` returns `null` for a rejection and `isEngagementFiltered()` returns
   `false`, so a screen reaching for either and stopping there renders the **unfiltered** list for a
   filter the URL plainly carries. `engagement-resolve.ts` handles the `rejected` kind explicitly
   for exactly that reason.
2. **Resolution happens inside `loadForOperator`, not beside it.** `confidence: high`. Resolving
   outside would give a gated visitor two notices about one missing session, and would leave
   `unavailable` meaning "you are not signed in" rather than "an operator asked and the read
   failed".
3. **`/waits` passes a resolved slug to `listWaits` rather than an id.** `confidence: high`.
   `listWaits` already took `engagementSlug`; the resolution in front of it is what makes
   `engagementIdForSlug`'s `invalid_request` throw unreachable, so FR-96c never renders as "this
   screen could not be read". Costs one extra indexed lookup on a filtered request, which I judged
   cheaper than reworking the store.
4. **`/registry` resolves in memory from the list it already read, with no `getEngagement` call.**
   `confidence: high`. One read decides both the rows and whether the slug exists, so the screen
   cannot hold two answers to one question. It is also why `/registry` has no `unavailable` branch:
   a failed read is already the gate panel.
5. **Scoped empty-state sentences on `/runs`, `/questions`, `/waits`.** `confidence: high`.
   "No fleet run has been ingested yet." under `?engagement=acme` reports an empty ledger on a
   request that looked at one engagement. `/work-items` needed nothing — its `query.filtered`
   variants already covered it.
6. **`withListFlag` as a shared module rather than two inline copies.** `confidence: med`. Two
   screens, five lines each; the shared version exists because the literal it replaces is exactly
   the shape that drops a filter when a second parameter appears, and that argument belongs in one
   documented place.
7. **The six answer screens' pages were not touched at all.** `confidence: high`. They already
   satisfied FR-96 and FR-96c; the unit's instruction was to adopt the primitive, and adoption there
   is a parser-level rename.
