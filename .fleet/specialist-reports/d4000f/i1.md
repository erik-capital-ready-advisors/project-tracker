### Two design calls worth stating rather than burying

**No `collides_with` foreign key, deliberately.** The obvious modelling of "both rows stand and the
collision is marked" is an edge from the planned row to the ingested one. It cannot be built: where
no shared key exists you cannot identify *which* two rows correspond except by matching prose, and
Q13 excludes prose similarity **absolutely**. A pairwise edge would have to be populated by the
exact mechanism the ruling forbids. So the mark is a property of one row — "a reconciliation was
attempted here and no key existed to carry it". Queued as a question.

**`plan_reconciliation` carries a `keyed` member nothing writes.** FR-90's merge half is deferred by
CR-005 §3.1a, so M2.9 only ever writes `collision`. The member is declared now because adding an
enum member later re-runs `create type` under `supabase db push`, which this repo has already been
bitten by. The CHECK constraint makes it unusable dishonestly: `keyed` without a `plan_ref` is
refused.

| Table | Class | Source | At rest | Retention | Deletion path |

| `work_item` (existing cols) | sensitive | spec §7a | pgcrypto on `description`, `raw_status` — unchanged | §7a Q3 baseline: indefinite | `purge_engagement()` (M1.10), untouched by this unit |
| `work_item.created_at` / `.updated_at` | sensitive tbl / metadata col | §7a by analogy | clear — timestamps, no prose | with the row | with the row |
| `work_item.plan_ref` | sensitive tbl / identifier col | §7a by analogy | **clear** — see below | with the row | with the row |
| `work_item.plan_reconciliation` | sensitive tbl / enum col | §7a by analogy | clear — closed enum, no prose | with the row | with the row |

**Why `plan_ref` is clear, and why this is §7a rather than a guess.** §7a names exactly two
encrypted columns on `work_item` (`description`, `raw_status`) and states the pattern explicitly one
row up: `requirement` is `sensitive` with "**pgcrypto column on `text`**; `ref` and `section` left
clear". `defect.title` is left clear on the same reasoning. `work_item.unit` — the *existing*
reconciliation key on this very table — is clear. `plan_ref` is an identifier of exactly that kind.
It is also load-bearing: an encrypted column cannot be indexed or matched, so encrypting the
reconciliation key would delete the requirement it exists for. **Queued anyway**, because §7a does
not name this column by name and the standing rule is that a column §7a is silent on gets recorded
rather than decided quietly.

**No new prose column was added, and none was needed.** A plan task title parsed from `### Task N:
<title>` is client prose and would inherit `sensitive` — it maps onto the existing, already-encrypted
`work_item.description`. i2/i3 should use that column rather than introduce a second one.

Controls from §7a: **4** · from baseline: **0** · **NOT VERIFIED: 2** — the two rate-limit and
security-header rows below, neither of which this unit touches.
Unclassified tables I refused to guess at: **none** — no table was created.

**B29, named because the brief requires it.** Every operator read still runs as `service_role`,

## The nullable-column blast radius — the finding that outlives this migration

The brief asked for every read that assumes `execution_mode` is non-null, "whether or not you had to
change it". **`pnpm typecheck` passes with zero errors after the column became nullable, and that is
the problem, not the reassurance.** The row interfaces are hand-written and do not derive from the
generated `Tables<"work_item">`, so widening the database type reaches nothing.

**Measured, not reasoned** — by running the real exported functions and deleting the probe after:

```
fromExecutionMode(null)                → "fleet"
fromExecutionMode(undefined)           → "fleet"
fromExecutionMode("fleet")  [control]  → "fleet"
fromWorkStatus("pending")   [control]  → "pending"
fromExecutorKind(null)                 → "unassigned"   ← this one is safe
```

Two distinct silent failures, at two different sites:

| Site | What happens when a planned row arrives |
|---|---|
| `src/lib/server/answers/from-db.ts:95` `fromExecutionMode` — reached from `answers/load.ts:313`, `detail/work-item.ts:195`, `runs/detail.ts:198` | Returns **`"fleet"`**. A planned row reads as fleet work on `/next`, `/committed`, the work-item detail view and the run detail view. **This is precisely FR-91's "nobody has started this" reading as "this is in flight".** |
| `src/lib/server/workitems/list.ts:122` + `:216` — `WorkItemRow.execution_mode: StoredExecutionMode`, passed through to `ExecutionModeChip` (`chips.tsx:235`) → `EXECUTION_MODE_LABELS[mode]` (`labels.ts:33`) | The raw `null` flows through a type that says it cannot be null. `EXECUTION_MODE_LABELS[null]` is **`undefined`**, so `/work-items` renders a **blank** mode chip with `data-verify-mode` unset. |

Also non-null-typed and now potentially wrong: `workitems/rules.ts:40` `StoredExecutionMode`,
`workitems/list.ts:68` `ListedWorkItem.executionMode`, `detail/work-item.ts:78`,
`runs/types.ts:118`, and `WORK_ITEM_SORT_COLUMNS` (`rules.ts:286`) which permits sorting on a column
that is now nullable — Postgres sorts NULLs last on ASC, which is defensible but undecided.

**i1 did not fix any of it, on purpose.** The fix is to widen the domain `ExecutionMode` to admit
null, which cascades into `ExecutionModeChip` and its two call sites — React components, which i1 is
forbidden to write, and which are u4's scope ("FR-91 planned + STALE visual treatment everywhere a
work item renders"). Changing it here would collide with u3/u4 at merge.

**Nothing is broken on this branch today**, because nothing writes a NULL yet. It becomes live the
moment **i3** writes the first planned row. i3 and u4 should treat this as the first thing they
handle. Queued as a question.

## Best-guess decisions

1. **`plan_ref` left clear, not encrypted.** §7a's stated pattern for a sensitive table is prose
   encrypted / identifiers clear (`requirement.text` vs `requirement.ref`), and `work_item.unit` is
   the same kind of column already clear on this table. Encrypting it would also make it unmatchable,
   destroying the requirement. Queued.
2. **The collision mark is a per-row state, not a pairwise edge.** A `collides_with` FK cannot be
   populated without prose matching, which Q13 excludes absolutely. Queued.
3. **Staleness derives from `updated_at`, maintained by a trigger.** FR-91 says "untouched".
   `created_at` was added too, so i4 can choose either without another migration. Queued.
4. **`keyed` declared now though nothing writes it.** Adding an enum member later re-runs
   `create type` under `db push`. The CHECK stops it being used dishonestly.
5. **Backfill of the 20 existing rows, stated not silent.** `created_at` moved back to
   `coalesce(started_at, ended_at)` where one exists — `now()` would assert these rows were created
   today. `updated_at` left at `now()`, which is literally true: this migration last touched them.
   Done before the trigger existed so it did not overwrite itself. No FR-91 answer depends on these
   values: all 20 rows are ingested, and staleness reads only planned rows.
6. **`work_item_planned_updated_idx` is partial, and that is safe.** The repo's prohibition on
   partial indexes is about *upsert conflict targets*, because PostgREST cannot restate a predicate.
   This index is not unique and is never a conflict target, so the rule does not reach it. Stated in
   the index comment so nobody "fixes" it later.
7. **The export needed no change, verified.** `export_everything()` projects `work_item` via
   `to_jsonb(r)`, so the four new columns are picked up automatically. FR-60 does not ship silently
   incomplete.
