### Six things i3 must know before it adopts this

1. **The primitive carries NO `'use server'` and NO `requireOperator()`.** It takes an
   already-authorised `ServiceClient` and owns the row shape; the caller owns who may call it —
   the same division `@/lib/server/ingest/persist` already makes. This is deliberate so that i3
   can reach it from a route handler under an agent bearer token, where `requireOperator()` cannot
   succeed by construction. **i3 must gate before calling.** `import "server-only"` keeps a Client
   Component out.
2. **`engagementSlug`, not `engagementId`.** The primitive resolves the slug against `engagement`
   with the client it was handed (not via `@/lib/server/registry/engagements`, whose exports all
   call `requireOperator()`), and refuses an empty or unknown slug in a sentence rather than
   letting a foreign-key violation surface as a 500. `ParsedPlan.engagement` from i2 is already a
   slug, so it drops straight in.
3. **The write is split on `plan_ref`, and this is load-bearing.** Rows with `plan_ref === null`
   go through a plain `.insert()` — i1's unique index on `(engagement_id, plan_ref)` is NULLS
   DISTINCT, so they never collide, and naming a conflict target that can never fire reads like
   idempotency and is not. Rows with a `plan_ref` go through
   `.upsert(rows, { onConflict: "engagement_id,plan_ref", ignoreDuplicates: true })` — that is the
   FR-90 idempotency i1 built the plain index for.
4. **`ignoreDuplicates` means an existing row is left exactly as it is.** A planned row that has
   since been dispatched must not be reset to `pending` by a second read of the plan it came from.
   If i3 needs the skipped set it must read back on `(engagement_id, plan_ref)`. Queued as a
   question with that best guess.
5. **The returned order is not the input order** — two writes, concatenated. Match a record to its
   input by `unit` or `planRef`, never by position. There is a test pinning this.
6. **`PlannedWorkRecord` carries no `description`.** The caller already holds the plaintext;
   echoing a §7a `sensitive` value back out of a persistence result is how it reaches a log line, a
   `data-verify-*` attribute or a redirect URL.

### What the tests do NOT prove

**The primitive is tested against `createFakeDb`, which is a table store, not a database.** It
enforces no foreign keys, no check constraints and no unique indexes beyond the one `onConflict`
key an upsert names, and it models neither `NULLS DISTINCT` nor PostgREST's
`resolution=ignore-duplicates`. So the tests prove this code **asks the database for the right
thing** — right columns, right values, right conflict target, nothing written on a refusal — and
they do **not** prove the database does the right thing with it. Specifically **NOT VERIFIED**:

- that `ignoreDuplicates: true` skips rather than clobbers a duplicate `(engagement_id, plan_ref)`
  against real Postgres;
- that a hand-entry row (`plan_ref` NULL) never collides with another under NULLS DISTINCT;
- that `encrypt_field` produces a real `\xc30d…` OpenPGP packet on this project's database (the
  fake's ciphertext is base64 behind a marker prefix).

Each needs a live service-role credential, which a worktree does not have and must not have. i1
observed the first two on the live index when it built it; this unit did not re-observe them.

## Best-guess decisions

Each of these resolved an ambiguity the spec did not settle. The first two are the ones most worth
a second opinion.

1. **The primitive takes a `ServiceClient` and gates nothing** (`high`). CR-005 does not say
   whether i3's plan-document path is operator-driven or agent-driven. Putting `requireOperator()`
   inside would close the door on the agent case; putting `'use server'` on it would open a
   browser-callable write endpoint. Taking an already-authorised client does neither, and matches
   `server/ingest/persist`. **If this is wrong, i3 is the unit that finds out**, so it is stated at
   the top of this report rather than buried.
2. **Module path is `src/lib/server/planned-work/`, not the suggested `src/lib/planned-work/`**
   (`high`). Repo convention: `src/lib/server/**` is where service-role code lives.
3. **`executor_kind` forced to `'unassigned'`, no form control** (`med`). Queued.
4. **`plan_ref` is not a form field** (`high`). Q13's key is "an id the plan carries and the
   manifest echoes"; an id Erik invents while typing is echoed by nothing, so the field would
   manufacture a key that cannot reconcile and would look like one that can. Hand entry always
   sends `null`.
5. **The action returns the new id and the client navigates**, rather than the server
   `redirect()`ing (`high`). `runOperatorAction` catches everything, and `redirect()` signals
   navigation by throwing — a redirect inside it is swallowed and reported as a refusal.
   `registry/actions.ts` solves the same problem by putting `redirect()` outside the try; that
   shape is unavailable to an action that must also return a refusal value.
6. **Archived engagements are not refused by the primitive** (`med`). Queued.
7. **Duplicate `plan_ref` is DO NOTHING, not UPDATE** (`med`). Queued.
8. **Form state is `RegistryFormState`'s neighbours, reused rather than duplicated** — the form
   composes `Fieldset` / `Field` / `TextField` from `@/app/registry/_components/field` (`med`).
   The alternative was a second spelling of a labelled field in a product with two typed-input
   screens.
9. **The action lives at `src/app/work-items/new/actions.ts`, not appended to
   `src/app/work-items/actions.ts`** (`high`). This unit owns `src/app/work-items/new/**` outright,
   so the file cannot collide at merge with a concurrent unit editing the listing screen's seam.
10. **`revalidatePath("/next")` on success** (`med`). A pending planned row is what FR-53 exists to
    answer before a run exists; a stale cache there would omit the item Erik just planned from the
    answer he planned it for.
