**The qualification.** "Every row is Erik's own hand work" is enforced by what the write path
*stamps*, not by *who calls it*: the endpoint is authenticated by an agent token carrying
`ingest:write`, and its own doc says a running agent posts to it mid-session. So any holder of that
token can create a session and it is still recorded as `hand` / `erik`. Nothing today writes a
session by another route — but the guarantee is a hard-coded literal, not an identity check.

**That is exactly why Q25's ruling is the right treatment and this unit implements it literally:**
the read layer counts *every* `work_session` row with no filter by executor, mode or `source`, and
the screen states that they are all Mode 2 capture. The day something else posts one, the sentence
is visibly wrong rather than quietly wrong. A test plants a session with
`source: 'some-future-writer'` and asserts it is still counted, so a future narrowing of this query
turns that test red.

### Q27 — how limb two is *not evaluated* rather than *false*

`UnevaluatedClause` is `{ evaluated: false; reason: string }` and **has no `met` field at all**. A
caller cannot read limb two as false because there is nothing there to read; `tsc` rejects adding
one, and `rule.test.ts` asserts `"met" in trigger.blockingMilestone === false` with a CONTROL
asserting the same check returns `true` for limb one, which *is* evaluated.

Both arms are plain objects rather than a `unique symbol` or a bare string literal. A string
sentinel would be absorbed into `string` and silently collapse the union (run `eb2490`), and a
symbol does not survive React Server Component serialisation — which this value must, since `u1`
renders it.

`TriggerOutcome` is therefore `'earned' | 'undetermined'` and **not** `'earned' | 'unearned'`.
`undetermined` means limb one did not fire *and limb two was never checked*. Asserting "unearned"
would be a claim about a clause nothing evaluated, which is the same class of error as a wrong
`done`. Queued as a question because FR-107 uses the word "unearned"; it does not change `u1`'s
brief, because FR-107's visually-distinct treatment keys off `actionable`, which is unchanged.

## Best-guess decisions

1. **Engagement count derives from `work_session.engagement_id`, not `work_item.engagement_id`.**
   Three reasons, in the order they mattered. (a) FR-105 defines hours as a sum over
   `work_session.duration_minutes` and FR-106 makes a *conjunction* of the two figures — a
   conjunction over two different populations is not a rule anyone can state on a screen, which is
   what FR-106 requires. (b) Derived separately, a stack could show three engagements and zero
   hours, a figure that is correct, unexplainable from the screen, and indistinguishable from a
   bug. (c) **The two populations are provably identical today**: `record.ts` sets
   `work_item.stack_id` (line 327) and `work_session.stack_id` (line 371) in the same function from
   the same local, and grep confirms nothing else in the product writes either column. So the
   choice costs no row now and stays coherent with FR-105 if they ever diverge.
2. **Register rows are ordered by name, ascending, and the order carries no claim.** Sorting by
   hours would imply "most used first" on a ledger where every stack holds zero minutes; sorting
   actionable rows to the top would make FR-107's distinction depend on position rather than on the
   treatment FR-107 asks for. `u1` may present differently.
3. **`hours` is `minutes / 60`, unrounded, and the threshold comparison is made in integer
   minutes.** The rule is *stated* in hours and *compared* in minutes, from one derived constant, so
   a stack on 479 minutes cannot be rounded into qualifying. Both `minutes` and `hours` are on the
   row; formatting is `u1`'s.
4. **`sessionsWithoutDuration` and `sessionsOnUnknownStack` are exposed even though both are zero
   today.** A NULL `duration_minutes` is permitted by the schema and would make hours understate
   silently; a `stack_id` matching no stack row is unreachable behind the foreign key. Both are
   counted so the FR-108 identities hold *by construction* and are asserted by a test —
   `sessionsTotal = withStack + withoutStack`, and `withStack = Σ row.sessions + onUnknownStack`.
5. **FR-109 writes an `audit_log` row** carrying actor, action and target id and **not** the value,
   per FR-59's "no record contents". This follows `registry/archive.ts` and `api/token-admin.ts`;
   `sessions/unassigned.ts` and `registry/engagements.ts` do not audit, which is a pre-existing
   inconsistency this unit reports and does not fix. Question 3.
6. **`agent_covering` is validated for shape only, never against a list of agents.** FR-109's whole
   premise is that `~/.claude/agents/` is unreadable from here, so an unrecognised name is stored as
   typed. The 96-character ceiling mirrors `LIMITS.stackName` and is a paste guard, not a schema
   rule. Clearing to `null` is a first-class operation, not an error.
