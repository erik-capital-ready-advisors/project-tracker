**RLS proven by policy, not flag.** All 21 tables reported `relrowsecurity = true` *before this
migration's policies existed* — the `ensure_rls` event trigger calling `public.rls_auto_enable()` sets
it. Evidence: a throwaway table I created and did nothing else to came out `relrowsecurity = true`
with **0 policies**. So the flag was measured worthless on this project. `pg_policies` shows 21/21
tables carrying a policy, 23 total.

**Probe proven against a known-bad case: YES.** Three independent negative controls:
- A function created *after* my `ALTER DEFAULT PRIVILEGES … REVOKE ALL ON FUNCTIONS` still showed
  `proacl = {=X/postgres,postgres=X/postgres,service_role=X/postgres}` — the leading `=` is PUBLIC.
  The detector fires.
- A deliberately-open table (`grant select to anon` + permissive policy) returned **HTTP 200 with real
  rows** to the publishable key, while its `relrowsecurity` was *also* `true`. Dropped afterwards;
  `leftover_zz_objects = 0`.
- `app.is_operator()` returned **true** for role + aal2 (below), so the chokepoint is not stuck closed.

**anon probes** (publishable key, which is public by design — it ships in the browser bundle):

| Probe | Observed |
|---|---|
| `GET /rest/v1/contract_milestone` | `401` `42501 permission denied for table contract_milestone` |
| `GET /rest/v1/agent_token` | `401` `42501 permission denied for table agent_token` |
| `PATCH /rest/v1/engagement?id=eq.000…000` | `401` `42501 permission denied for table engagement` |
| `POST /rest/v1/rpc/decrypt_field` | `401` `42501 permission denied for function decrypt_field` |
| `POST /rest/v1/rpc/…` with `Content-Profile: app` | `406` `PGRST106 Only the following schemas are exposed: public, graphql_public` |

That last line is the observation behind the whole design: helpers live in `app`, which is confirmed
unexposed, and the per-name REVOKEs are the second layer rather than the only one. Note the failure
mode is `401`/`42501`, **not `200 []`** — the grant is gone, not merely filtered, so the refusal is
diagnostic rather than ambiguous.

**Column encryption read back as ciphertext: YES.** `contract_milestone.amount` for a seeded row:
`\xc30d040703024a1e726c101958c1…`, 73 bytes, `pg_typeof = bytea`, `amount::text ~ '7500'` → **false**.
`public.decrypt_field(amount)` → `7500.00`; `.notes` → the plaintext sentence. Probe row deleted after.

**Decrypt helper raises rather than returning NULL.** Renamed the Vault secret via
`vault.update_secret` inside a transaction, called `app.decrypt_field`, observed
`raised_instead_of_returning_null = true` with message `delivery_ledger: Vault secret
"delivery_ledger_column_key" is absent or unreadable`; renamed back. Post-check: `key_rows = 1`,
`stray_probe_names = 0`, existing row still decrypts to `7500.00`.

**Function ACLs.** All 18 functions: `search_path = ""` on every one, `prosecdef = true` on 17 (the
exception, `app.looks_like_secret`, is called only from inside a SECURITY DEFINER trigger and needs no
grant), and **no leading `=` entry on any of them**. `anon` appears on none. `authenticated` appears on
exactly two — `assurance_satisfied()` and `is_operator()` — both required because RLS policy
expressions are evaluated with the querying role's privileges, and both disclose one boolean about the
caller's own session.

**MFA / new-account truth table** (synthetic `request.jwt.claims`):

## Prior Fleet Learnings Used

- `Knowledge/A fresh Supabase project grants anon and authenticated full table privileges, and TRUNCATE ignores RLS.md`
  — **CONFIRMED on this project.** `pg_default_acl` for role `postgres` in `public` read
  `anon=arwdDxtm/postgres` and `authenticated=arwdDxtm/postgres`, TRUNCATE included. Drove the
  default-privilege revokes in migration 000100 *before* any table existed, which is why all 21 came
  out with zero `anon`/`authenticated` grants. Its third specific — that
  `ALTER DEFAULT PRIVILEGES … ON FUNCTIONS` is a no-op against PUBLIC — was **re-measured and confirmed**
  by the negative control. Its point about `200 []` vs `42501` is why I revoked grants rather than
  relying on policies alone.
- `Knowledge/Supabase SECURITY DEFINER views bypass RLS - check the grant table, not the linter.md`
  — **CONFIRMED, and it changed the design.** I created **no views at all**, and read `proacl` and
  `aclexplode` directly rather than trusting `get_advisors`. Vindicated: the advisor reported zero
  findings against my objects, but it was the grant table that actually established that.
- `Knowledge/An RLS DELETE refusal is silent - assert affected row count, not absence of error.md`
  — **CONFIRMED and applied.** Every probe here has a positive control, and I seeded `audit_log`
  before testing the append-only trigger precisely because that note says an empty-table security
  test is close to worthless.
- Brief's claim that `public.rls_auto_enable()` is not exploitable via `/rest/v1/rpc/` —
  **CONFIRMED with a nuance worth recording.** `POST /rest/v1/rpc/rls_auto_enable` as `anon` returns
  `400 0A000 cannot display a value of type event_trigger`, **not `42501`**. The grant is live and the
  call reaches the function; only the return type stops it. Supabase's own advisor raises it as a WARN
  saying it "can be executed by the `anon` role", which is a true positive on the grant and a false
  positive on exploitability. I left it alone — it is a platform-managed object this build did not
  create, and revoking on it risks the event trigger for no measured gain.
- Brief's `supabase_vault` item, marked NOT VERIFIED — **now settled by observation:** it **is**
  pre-installed, version `0.3.1`, schema `vault`. Also: `vault.update_secret` exists with signature
  `(uuid, text, text, text, uuid)`, which is what made the missing-key probe possible;
  `postgres` cannot `UPDATE vault.secrets` directly (`42501 permission denied for table secrets`).

## Best-guess Decisions

- **Enum where the spec states the closed set, `text` where it does not.** 17 enums, all traceable to
  a numbered FR. Inventing a value set the spec never wrote is the same move as widening a regex to
  make a stubborn row classify.
- **Encrypted three columns §7a does not name**, on tables it classifies `sensitive`, because the
  baseline governs where §7a is silent and §7a wrote its waivers explicitly where it wanted them.
  Resolved upward, and queued.
- **Helpers in an unexposed `app` schema, with thin `public` wrappers granted to `service_role` alone.**
  The exposed API surface is exactly six functions. Consequence i4 must know: **decryption is
  service-role-only, so a decrypted read bypasses RLS.** If session-scoped decrypted reads are wanted,
  the shape is a `security_invoker = on` view per table plus `EXECUTE` on `app.decrypt_field` for
  `authenticated`. I did not build that — it is not in scope and it widens the oracle surface. Flagging
  it because the alternative is i4 quietly routing everything through service_role and RLS becoming
  decorative.
- **`work_item.external_wait_id`** added as a one-to-many FK: §7 states "an external wait blocks many
  work items" but lists no join entity among the 21, and adding a 22nd table would break the count.
- **Seeded the `unassigned` engagement row** so FR-26 has somewhere to put an unattributable session.
- **`agent_token.created_at`** added though §7's field list omits it — §7a's stated retention ("until
  revoked, then 90 days for audit") needs a dated record.
- **No natural unique key on `open_question`**, stated in a table comment: `question` is
  non-deterministic ciphertext so it cannot be a dedupe key, and `(engagement, run, unit, section)` is
  not unique. FR-22 idempotency there needs a plaintext digest column or delete-and-reinsert-per-run.
  i4's call.
- **Recommended agent-token plaintext shape `dl_<row id>_<random>`**, in the table comment: without an
  id in the token, verifying a bearer credential means bcrypt-comparing every stored hash on every
  request, which is an O(n) cost on an unauthenticated path.
- **Fixed-window rate limiter**, with the boundary-burst weakness (true worst case 2x nominal across a
  boundary) stated in the migration. Prune function provided but **not scheduled**, per FR-62.
- **`APP_ENCRYPTION_KEY_NAME`** already in `.env.example`; I matched its value
  (`delivery_ledger_column_key`) as the Vault secret name. The database function hardcodes the name
  rather than reading the env var — the two must be changed together. **No new env var is required by
  this unit.**
