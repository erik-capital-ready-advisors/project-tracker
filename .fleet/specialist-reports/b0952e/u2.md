## What I built

### FR-9 + FR-13 — the one form in the product

FR-13 says engagement and milestone records are the only data Erik types and everything else is
captured or derived. That makes this form the entire manual-input surface, so it is grouped into
three fieldsets — who the work is for, where its artifacts live, which accounts it was provisioned
into — rather than a flat list of fourteen inputs in which the third group is invisible.

It validates nothing itself. `validateEngagement` owns the rules and the database owns FR-78, and a
second copy of either here would drift from the first and answer one question two ways.

### FR-12 — the dangling reference is marked in place, not toasted

`i5` returns `unknownAcceptanceRefs` on **every read**, not only at write time, and the table marks
them every time it renders. A warning shown once at save is gone by the time anyone looks; a
reference that is wrong stays wrong until someone fixes it, so it stays marked until someone does.
The write path reports it too — `submitMilestone` deliberately does **not** redirect on success, and
the milestone dialog stays open when a save comes back with findings, because the moment to fix a
typo'd `FR-` reference is while the form is still open.

**It is not rendered in fuchsia.** A dangling reference is not an unparsed record — it parsed
perfectly and points at nothing, which is the opposite failure. It takes the `blocked` family with a
dashed outline. A test asserts no registry surface emits `state-unparsed` at all, and it is proven
able to fail. Queued as a question, because the colour is Erik's call.

### FR-78 — the refusal is rendered as itself

`errors.ts` composes a sentence naming the offending column from this build's own allowlist. My
form-state seam passes `ApiError.message` through untouched and `FormBanner` renders it as "Not
saved" with the sentence. An unrecognised throw gets a generic sentence instead, because that is
exactly the case where a mechanism would leak. The form also explains the rule before it fires, and
an e2e test asserts the words "identifiers, never secrets" are on the page.

### FR-11 — two dates, two actions

Two separate forms, two separate submits, two separate server actions. A form that makes you
re-state a value you already gave is a form that eventually gets a wrong value re-entered into it.
An empty date clears the field, which is how a mis-click is undone without a second concept.

### The numbers that must not lie

- A milestone amount that did not decrypt renders **"unreadable"**, never `$0` and never blank.
- Totals across mixed currencies render **"not summed"**, never a figure.
- "No milestones yet" and "mixed currencies" are reported differently, even though
  `milestoneTotals()` answers `currency: null` for both.
- An absent identifier renders **"not recorded"**, never blank — a blank cell and a cell nobody
  rendered look identical, and that matters most on the columns saying which account a client's
  data is sitting in.

### The operator gate

Every registry screen reads the operator context and renders one of six named refusals rather than
throwing. `requireOperator()` throws an `ApiError`, which is right for a route handler and wrong for
a screen: it renders the error boundary, and "sign in", "enrol a second factor", "present the one
you have", "ask for a role" and "this deployment has no database configured" are five different
mornings. **The gate decides what to draw; it is not what authorises** — every action still runs
`requireOperator()` as its first line before a service-role client opens.

The `no-role` panel says in as many words that this is **not a missing account**, because `i1`'s
deny-by-default means an `aal2` operator with no role reads zero rows, which is indistinguishable
from "no such account" if the UI is careless. A test pins that sentence.

## What looking at it changed

I ran `next build && next start`, drove it in a browser at 1280×900 and 390×844 in both themes, and
two things were wrong in ways no test would have caught.

**1. FR-12's finding was clipped off the right edge.** With the milestone table in a
`lg:grid-cols-[minmax(0,1fr)_22rem]` main track, the table needed **811px** in a **654px** container
— measured, not eyeballed. Paid and the row actions were behind a horizontal scrollbar, and so was
the acceptance column. The requirement that exists to make a dangling reference *visible* was the
thing being hidden. Every way of fitting six columns into 654px costs something §5a asks for, so the
sidebar went away instead: provisioning is a one-lookup reference, not something scanned in parallel
with milestones. Both tables now measure **0px overflow**.

**2. Identifiers wrapped mid-token.** In the 22rem sidebar, `onpvolboecjpdkvurjaf` rendered as
`onpvolboecjpdkvurj` / `af`. These identifiers exist to be compared against an account page in
another tab, and breaking a token at an arbitrary point is the one shape that makes comparison
harder. Labels now sit above values.

Also fixed by looking: the gate panel spanned wider than the form it was about (one measure now),
and the submit row crowded at 390px.

### A test I corrected rather than kept

One mutation initially **survived**: removing `formatDate`'s ISO passthrough. I had claimed in a
comment that round-tripping through `Date` would shift a due date west of UTC. **I measured it, and
I was wrong** — a bare `YYYY-MM-DD` is parsed as UTC and survives `toISOString()` in every timezone
(checked at UTC, UTC−7 and UTC+14). The two implementations agree, so the mutation was equivalent,
not a hole.

Measuring it did surface a real defect next door: a timestamp stating **no zone** is parsed as local
time, and at UTC+14 `2026-09-01T00:00:00` renders as `2026-08-31` — a milestone shown as submitted
the day before it was, on some machines and not others. `formatDate` now takes the date the string
carries; there is a test for it, and the mutation now bites. The comment says what I measured rather
than what I assumed.

## Finding that affects other units: WebKit cannot run this app over plain HTTP

The mobile Playwright project (iPhone 13 / WebKit) failed one test, and it looked like a UI defect
in my link. It is not.

**Measured:** this branch serves `Content-Security-Policy: … upgrade-insecure-requests` and
`Strict-Transport-Security: max-age=63072000; includeSubDomains` (i4's work, correct for
production). Chromium exempts `127.0.0.1` from the upgrade; **WebKit does not.** Against
`next start` over http, every script request becomes `https://127.0.0.1:…` and fails TLS:

```
requestfailed: https://127.0.0.1:3150/_next/static/chunks/turbopack-….js
  A TLS error caused the secure connection to fail.
```

So **no client JavaScript loads at all on the mobile project**, and there is no client router to do
any navigating. Server-rendered assertions pass, which is why 10 of 11 tests looked fine and only
the one needing hydration failed — a shape that reads as a flaky UI bug and is not.

This is the security header working. **It must not be weakened to make a test pass.** I marked the
one client-navigation test `test.skip` for WebKit with the measurement written next to it, and
rewrote the flow test to assert the link's target and the destination screen without depending on
hydration, so it holds in both projects. Running the mobile project against client-side behaviour
needs `PLAYWRIGHT_BASE_URL` pointed at an https preview deployment.

Two consequences for the run:
- **u1's "mobile project unexecuted" NOT VERIFIED is now closed** — I installed WebKit and the full
  mobile project runs (47 passed / 1 skipped across both).
- **Any unit asserting client-side interaction on the mobile project will hit this**, and should be
  told before it spends the time I spent.

Worth a vault note: *"A CSP with `upgrade-insecure-requests` makes WebKit unable to load any
subresource from a plain-HTTP localhost server, so a Playwright WebKit project against `next start`
silently loses all client JS while server-rendered assertions keep passing."* Evidence: request
failures above, observed on `next@16.3.1` / WebKit 26.5 against `127.0.0.1:3150`, with the headers
read back from `curl -D-`.

## Best-guess decisions

1. **Form-action wrappers live in `src/app/registry/actions.ts`, not `src/lib/server/`** — that tree
   is out of my lane. They are a `FormData` seam and nothing else.
2. **`export const dynamic = "force-dynamic"` on all four routes.** Per-operator, never cached across
   sessions. `cookies()` forces it anyway; stating it puts the reason at the top of the file.
3. **Native `<label>` rather than shadcn's `label` primitive.** Same job, no dependency, and no new
   file in `src/components/ui/` while u4 is editing that tree concurrently.
4. **`autoComplete="off"` on every registry field.** A client's name, contract terms and provisioning
   identifiers are not things to leave in a browser's autofill store. Asserted in e2e.
5. **`<input type="date">` for all three dates.** Native picker, and it emits exactly the
   `YYYY-MM-DD` that `validateMilestoneDate` expects.
6. **A non-numeric amount is passed through as `NaN` rather than coerced.** `validateMilestone`
   refuses it with a sentence; silently turning `"12,000"` into an empty amount would drop a
   client's money out of the record without saying so. (Commas and `$` are stripped first.)
7. **`getOperatorContext()` rather than `requireOperator()` in the gate**, so the five refusals stay
   distinguishable. The boundary is unchanged and remains in the actions.
8. **The engagement list carries no milestone counts or totals** — N+1 decrypting reads. Queued.
9. **The detail page reads milestones twice** (`listMilestones` + `milestoneTotals`), concurrently.
   Re-deriving the sums locally would be a second implementation of §7a's money rules. Queued.
10. **Static `metadata` on the detail page rather than `generateMetadata`.** A `generateMetadata`
    that called `getEngagement` would throw for an unauthenticated visitor and turn a rendered
    refusal into an error page.
11. **The `unparsed` count is left to the shell.** u1 mounts it globally, which is what makes FR-58
    structural; nothing in the registry is parsed, so there is no unit-local count to report. It
    reads "unparsed count unavailable" — the honest third state, never `0`.
