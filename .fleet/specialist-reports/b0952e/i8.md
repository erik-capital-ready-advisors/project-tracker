## The exact call shape `d1` uses to post a deploy

```
POST https://<deployment-host>/api/ingest/release
Authorization: Bearer dl_<uuid>_<hex>          # a token carrying ingest:write
Content-Type: application/json
```

```json
{
  "engagement":       "delivery-ledger",
  "identifier":       "dpl_9xKq2mVn",
  "environment":      "preview",
  "url":              "https://delivery-ledger-9xkq2mvn.vercel.app",
  "deployed_at":      "2026-08-19T18:04:11Z",
  "recorded_by":      "fleet:b0952e/d1",
  "requirement_refs": ["FR-73", "FR-74 to FR-76"]
}
```

Field notes, in the order they will bite you:

- **`engagement` is the slug, not the uuid.** An unknown slug is a `400`, not a silent filing under
  `unassigned`. Queued — see Questions.
- **`identifier` + `environment` + `engagement` is the idempotency key.** Post the same deploy twice
  and you get one row.
- **`source` is not accepted.** FR-73 defines it as *how* the release was recorded; this route pins
  `ingested`. Sending `"source": "declared"` is ignored, not honoured — there is a test.
- **`environment` is free text**, stored verbatim. §7a and FR-73 state no closed set and i1's rule is
  `text` where the spec does not, so no enum was invented. `preview` and `production` are the
  vocabulary this build uses.
- **`requirement_refs` entries may be a single ref, an FR-19 range, or a sentence containing them.**
  All three range spellings i2 supports work: `FR-74 to FR-76`, `FR-1–FR-3`, `FR-36, FR-39 to FR-41`.
  An entry naming no `FR-nn` at all comes back under `requirement_refs.unparsed` and is stored
  nowhere.
- **`deployed_at` must be a date the system can read.** An unreadable one is a `400`. It is not
  quietly stored as null, because "no deploy date was recorded" is a different and false claim.
- **`url` must be `https`, must carry no `user:pass@`, and has its credential-shaped query
  parameters stripped.** `x-vercel-protection-bypass` is stripped by name; any parameter whose
  *value* is secret-shaped is stripped too. Every removal is named back to you in
  `data.url_params_stripped`. A preview deploy URL with a bypass token is a credential; post it and
  the ledger stores the URL without the key and tells you it did.

## Best-guess decisions

Each of these is queued in `.fleet/questions-i8-b0952e.jsonl`; the code proceeds on the guess.

1. **A release naming a requirement that does not exist gets its link row written and is reported as
   `unresolved`.** FR-12/FR-65 forbid *silent acceptance*, not storage, and CLAUDE.md says to record
   both sides where two artifacts disagree. Dropping it would lose data permanently whenever a fleet
   run posts a deploy before the engagement's requirements are ingested. No requirement is ever
   created. Reversing this is one line in `linkRequirements`.
2. **An unknown engagement slug is a `400`, not a filing under `unassigned`.** FR-26's fallback is
   written for a *session*, which resolves to an engagement by heuristic; a release names its
   engagement outright.
3. **`release.identifier` gets FR-78's secret-shape refusal, with a hex-only carve-out for git
   object ids.** FR-78 names only `engagement`'s five columns and there is no trigger on `release`,
   so this is an application control I added. Without the carve-out a full 40-character commit SHA —
   FR-73's commonest "deploy reference" — would be refused as a high-entropy blob.
4. **The endpoint's `unparsed` count is `work_item` rows with `status = 'unparsed'`, globally.**
   Nobody has defined this population and i5/i6 must match it or the six endpoints will disagree.
   Flagged low-confidence.
5. **`source` is not readable from the request body.** A caller does not get to declare how it was
   recorded.
6. **Numbers that are mine, not the spec's:** 64 KiB body cap, 2000 expanded refs, 500-entry
   `requirement_refs` array, 200/64/2048/200-character field caps, 500-item `.in()` chunks. All are
   an order of magnitude above any legitimate use in §7a's stated traffic shape.
