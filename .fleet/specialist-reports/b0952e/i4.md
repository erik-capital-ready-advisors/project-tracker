## What I built

### The bearer-token path (FR-4)
Token plaintext is `dl_<row uuid>_<64 hex>`. The id is in the token so verification is one indexed
lookup plus **one** bcrypt comparison rather than a comparison against every stored hash — an O(n)
bcrypt on an unauthenticated path is a CPU-exhaustion surface, not just slow.

**Only the 64-char secret segment is hashed**, and that is measured rather than assumed: pgcrypto's
`crypt(…, gen_salt('bf', …))` truncates its input at exactly 72 bytes, so hashing the 104-character
full plaintext would put 32 characters of the secret past the boundary where they contribute nothing.
The observation is in Verification.

### The order of the auth checks is the security property
Header → shape → row lookup → **verify secret** → revoked? → expired?. Unknown id and wrong secret
return a **byte-identical** `invalid_token`, so ids cannot be enumerated. `token_revoked` and
`token_expired` are specific *only after* the caller proved possession, at which point the
information is diagnostic rather than a probe. Tested both ways.

### FR-5 refusal, and FR-59's "no record contents"
Covered in their own sections below.

### FR-8 rate limiting
Per token, through `public.check_and_increment_rate_limit`. **Fails closed** — an RPC error refuses
the request rather than serving it unmetered.

### FR-6 / FR-59 audit
Exactly one `audit_log` row per request on **every** path, including refusals and including a handler
that threw. The writer **fails closed**: if the audit write fails, the request fails, because "every
token use is written" quietly becoming "most" is invisible precisely when something is wrong.

### `next.config.ts` — both required changes
`agentRules: false` and the full header set. Both observed; see Verification.

**Five things that will bite you if you don't read them:**

1. **Use `ctx.db`, never `createServiceClient()` inside a handler.** The scoping in `agent-db.ts` is
   the entirety of FR-5's enforcement. A handler that makes its own client silently opts out.
2. **`operator.ts` and `token-admin.ts` are deliberately not re-exported from `@/lib/api`.**
   `operator.ts` carries `import "server-only"`, and folding it into the barrel would make any Client
   Component that imports one API helper fail to build for an unrelated reason.
3. **`requireOperator()` at `aal1` is not "no account".** The `operator` row is unreadable below
   `aal2` because `app.is_operator()` gates it. `OperatorContext` returns `mustVerifyMfa` and
   `mustEnrolMfa` separately for exactly this reason. Treating a null profile as "no such user" is how
   Erik gets locked out of his own product.
4. **`select('*')` on `engagement` is refused for agents.** See the §7a column restriction below.
5. **`apiOk`'s `unparsed` is optional and omitted means "not counted".** Passing `0` asserts that
   everything classified. FR-58 wants the real count.

### FR-5's refusal is application-layer, and this is the honest statement of it

Per Erik's answer 7, in his terms:

> This is a weaker guarantee than §7a implies, because the route handler reads with the service-role
> key which holds `BYPASSRLS`. **The control is application-layer, not database-enforced, and this
> report does not claim §7a's refusal is enforced by RLS. Scoped Supabase JWTs are the real fix and
> belong in Phase 2 planning, not a silent downgrade.**

Concretely, `agentScopedDb` catches: a direct `.from()` on a forbidden table; a PostgREST embed by
table name or alias; an embed by **foreign-key constraint name** (`acceptance_criterion_milestone_id_fkey`,
which contains no table name at all — enumerated by hand and tested); the credential/limiter RPCs;
and the `engagement` column allowlist, including inside an embed.

It does **not** catch: a handler that calls `createServiceClient()` itself; a raw `fetch` to
`/rest/v1/`; or **a future foreign key to a forbidden table whose constraint name nobody adds to
`AGENT_FORBIDDEN_EMBED_ALIASES`**. That last one is a hand-maintained coupling to the schema and is
precisely the fragility a database grant would not have.

## Best-guess decisions

- **Only the secret segment is bcrypt-hashed**, not the full plaintext. Forced by the measured
  72-byte truncation.
- **Rate-limit numbers are mine** — §7a gives the shape, not the figures. 60/min and 120/min. Queued.
- **`engagement` column allowlist enforced strictly**, including refusing `select('*')`. §7a says
  agents may read "name and slug"; refusing too much fails loudly in a test naming the column, and
  allowing too much leaks quietly. Those are not symmetrical. Queued.
- **`operator`, `agent_token` and `audit_log` added to the agent denylist** although FR-5 names only
  `contract_milestone` — §7a's "who may read" column says "operator only" for all three, and an agent
  token is not the operator.
- **`decrypt_field` and `encrypt_field` remain callable by agents.** §7a says work-item, blocker,
  requirement and question prose is read by "operator, agents, **decrypted server-side**", so blocking
  them would break the answer endpoints. The oracle this creates is bounded by the table refusal: an
  agent cannot obtain `contract_milestone.amount` ciphertext to feed it.
- **`audit_log.capability` stores the wire spelling**, pinned by a check constraint, because the audit
  log is what a human reads and FR-5 spells capabilities with a colon.
- **Audit `actor` for operator actions is the `auth.users` UUID, not the email** — an email would put
  personal data into a table §7a classifies `internal` precisely because it holds none. Queued.
- **Rate limiting runs after authentication**, so a stranger cannot burn a real token's window without
  holding it. Cost: an unauthenticated flood is bounded only by the platform, which is acceptable
  because §7a states there is no public surface and authentication is one lookup plus one bcrypt.
- **`last_used_at` is best-effort** and its failure does not fail the request. The audit log is the
  authoritative record of use (FR-6) and is already written by that point.
- **Rotation issues the new token before revoking the old one**, never the reverse — the other order
  opens a window with no valid token, i.e. an outage caused by routine credential rotation.
- **Revoking an already-revoked token is a success no-op** and writes no second audit row.
- **Nonce-based CSP, accepting that it forces dynamic rendering.** The root layout awaits `headers()`,
  which makes all 13 routes dynamic. Correct for this product regardless — §7a says there is no public
  surface and every screen reads live per-request data. **Partial Prerendering is now incompatible and
  must not be enabled without replacing this approach.**
- **`vitest.config.ts` aliases `server-only` to a no-op.** It throws on import outside an RSC, which
  is the point of it and also makes any module importing it untestable. The guarantee still holds —
  Next's bundler enforces it at `pnpm build`, a separate gate that still runs.
