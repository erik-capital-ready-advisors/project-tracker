## The `unparsed` population I defined, and why

**Every record in the ledger that a classifier could not classify, across every engagement,
unfiltered.** Three tables — the only three in the 21-entity schema whose enums carry an `unparsed`
member:

| Table | Predicate | Where it comes from |
|---|---|---|
| `work_item` | `status = 'unparsed'` | FR-15. The population i5, i6 and i8 already agreed on; preserved. |
| `defect` | `severity = 'unparsed' OR status = 'unparsed'` | **FR-64 in terms**: *"A finding paragraph the parser does not classify is stored `unparsed` and counted per FR-58."* Not a judgement call — the spec settles it. |
| `test_result` | `status = 'unparsed'` | **Mine, not the spec's.** Queued. |

Four decisions inside that, each of which u3 and every future screen inherits:

1. **A defect unparsed in both columns counts once.** The population is *records*, not fields.
   "How many rows could the system not classify" is what FR-58 asks, and counting a row twice
   inflates the number with no corresponding record for Erik to go and look at. One `.or()` request,
   not two counts summed.

2. **Global, never narrowed by the caller's filters.** FR-57 says the endpoints carry "the same
   filters the screens offer" and it would be natural to narrow the count with them. It is not,
   because a filtered count can read `0` while the ledger holds unclassified records — Erik filters
   Committed to one clean engagement, sees "0 unparsed", and reads it as *the system classified
   everything*. That is this product's founding failure reached through the filter control instead
   of through a parser. Also: **u1 already mounted the badge in the app shell**, above the screens
   and outside any filter, and one definition means those two numbers must be the same number.

3. **The total is `null` if any component fails — never a partial sum.** A partial total understates,
   and an understated unparsed count is indistinguishable from a healthy one. This is the one place
   the conservative choice costs something real (a defect-table outage hides a good work-item count)
   and it is still right. `apiOk` omits an absent count from the envelope rather than sending `0`.

4. **The per-table breakdown ships alongside the total** (`unparsedBreakdown` on every answer
   payload), so a screen can show *where* the unclassified records are without redefining *what*
   they are.

**Reconciled, so exactly one definition exists in the tree.** `src/lib/server/releases/unparsed.ts`
was **deleted** — not shimmed, not re-exported — and `releases/handler.ts` repointed to
`@/lib/server/answers/unparsed`. `grep -rn "currentUnparsedCount" src/` returns my definition and
its two call sites. **Consequence for i8:** `POST /api/ingest/release` now reports a *larger*
number than it did, because it now includes unparsed defects and test results.

**Counted, never read.** Every predicate is on a clear enum column and `count: 'exact', head: true`
returns no row contents, so the FR-58 count crosses no §7a boundary even though two of the three
tables it counts are `sensitive`.

### One loose end I deliberately did NOT reconcile — flag for the orchestrator

`listWorkItems` in `src/lib/server/workitems/list.ts` (i6) returns a field also called `unparsed`,
computed as `items.filter(item => item.status === "unparsed").length` — **page-local, filtered, and
work-items-only.** It is a genuinely different quantity from FR-58's count and its docstring
describes it as "the count of rows this page could not classify", which is defensible as a *listing
statistic*.

**But it is named `unparsed`, and a screen rendering it next to the shell badge will show two
different numbers for what a reader takes to be the same thing** — which is precisely the failure
this unit was asked to end.

I did not change it, for one reason: **u4 is building the work-item screens against that surface
right now, in parallel.** Editing a function's return shape underneath a unit that is mid-flight is
how a merge produces something neither specialist tested. The safe fix is a rename
(`unparsedOnThisPage`) plus a call to `currentUnparsedCount` for the FR-58 badge, and it belongs to
whoever merges u4 — or to a follow-up unit. **Queued.**

### What an `answer:read` agent token can and cannot retrieve — be explicit, as asked

**`GET /api/answer/committed` answers `403 forbidden_table` to every agent token, always, with no
partial answer.**

§7a: `contract_milestone` is *"operator only; agent tokens are refused this table"*, repeated in
§7a's authentication posture. FR-54 says the answer lists milestones. Where a requirement and the
security posture collide, the posture wins — the alternative is guessing permissively at a written
boundary, which is where both of this practice's production incidents began. **Nothing about a
milestone reaches an agent: not the name, not the due date, not the acceptance refs, not the
coverage state**, because every field derives from a row in that table.

The route is registered anyway so FR-57 is true: it authenticates, rate-limits, writes its audit row
and then refuses with a code and a sentence naming the operator session. A 404 would read as "not
built yet" rather than "you may not have this". **The refusal is thrown by `agentScopedDb` itself,
not re-implemented here, so it cannot drift from the enforcement** — and mutation 13 confirms the
test sees it.

Two answers **degrade rather than refuse**, and say so in the payload:

- **`/api/answer/next`** — FR-53 orders by the nearest dated milestone, which needs
  `contract_milestone.due_date`. An agent gets `ordering: "fallback"` with
  `orderingUnavailableReason` naming §7a, **never `"milestone-due-date"` over a list sorted by
  something else.** Erik acts on the top row; a list claiming an ordering it did not compute is a
  wrong answer that looks right.
- **`/api/answer/bottleneck`** — same for "the nearest milestone at risk". `ranking:
  "unblocks-only"` with a stated reason.

The honest substitute for an agent wanting requirement-level coverage and shipped state without
commercial figures is `/api/answer/untested` and `/api/answer/broken`, which read no
`contract_milestone` row. That is named in the route docstring so a caller does not have to discover
it.

**The operator screens u3 builds call `blockedAnswer` / `nextAnswer` / `committedAnswer` /
`untestedAnswer` / `bottleneckAnswer` / `brokenAnswer` directly** with an unscoped client and
`milestones: true`, and get everything. That is why the ranking logic lives in the answer modules
rather than in the handlers.

  termination, stable order, `.in()` chunked at 500), and the FR-58 census uses `count: 'exact',

  billable whose covering test is currently red. Mutation 5 shows the short-page version returning a

All eleven are queued in `.fleet/questions-i7-b0952e.jsonl`; the code proceeds on the guess.

1. **`/api/answer/committed` refuses agent tokens entirely** rather than widening §7a to satisfy
   FR-54. The one place a spec requirement and the security posture collide, and the posture wins.
2. **FR-47's certifier is `test_result.certified_by`, with no fallback to `test_case.certified_by`.**
   A certification is an act performed on a particular run. Note the risk direction: a result with no
   certifier establishes *no* coverage, so this reading can only withhold coverage, never grant it.
3. **A null `evidence_scope` maps to `not-verified`,** putting the requirement in FR-49's `unproven`
   bucket. Same asymmetry — it can only withhold.
4. **`skipped` and `unparsed` test results map to `not_run`,** never to `pass`. They still displace
   an earlier pass as the latest result, so a test whose latest run nobody could read stops proving
   anything. That is deliberate and asserted.
5. **FR-52's owner is `blocker.owner` → `wait.owner` → `DEFAULT_BLOCKER_OWNER`**, and the work item's
   `executor` is never consulted. Nothing infers an owner from prose.
6. **FR-53's candidates are `pending` and `not_dispatched` only.** `unparsed` is excluded *and
   counted*.
7. **FR-56 ranks by transitive descendants**, with `directDependents` reported beside it so the
   number can be checked rather than trusted.
8. **An unrecognised query parameter or value is a 400**, not an ignored filter.
9. **A milestone whose amount will not decrypt is excluded from the totals and counted**, rather than
   failing the whole answer. i6's `decryptAll` throws for the batch — right for its ingest path,
   wrong for a read path where one bad ciphertext would take down every engagement's Committed.
10. **`test_result.status = 'unparsed'` is in the FR-58 population.** Mine, not the spec's.
11. **Numbers that are mine:** `limit` capped at 500, filter values capped at 200 characters, 5000
    results per test run, `.in()` chunked at 500. All an order of magnitude above §7a's stated
    traffic shape.

## Not done, deliberately

- **No HTTP write path for `test_result`.** `src/app/api/ingest/**` is another unit's ownership and a
  new `ingest:write` endpoint is a security surface, not a convenience. The persistence is complete,
  validated and tested; wiring it is three lines of the shape `release/route.ts` already has, and the
  exact call shape is documented on `recordTestRun`. **So FR-47 through FR-51 compute correctly and
  have no production data path yet — that is a real gap in M1.8 and it is queued, not implied away.**
- No export and no deletion path. M1.10 is BLOCKED on CR-002, which is not part of the spec basis.
- No React, no pages, no test suite beyond the colocated unit tests these rules require.
- `src/lib/database.types.ts` not regenerated and no delta hand-added — none was needed.

**Nothing here is deployed.** This is code on `agent-build/2026-08-19-b0952e` in a worktree,
committed and not merged. Code on a branch is not on `main`, and nothing reaches production until it
is merged and deployed.
