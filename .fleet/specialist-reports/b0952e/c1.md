## The distinctions I had to keep apart, and the words I chose for each

This is the substance of the unit. Every pair below is two different words on screen, never one.

### `unparsed` — never "other", "misc" or "unknown status"

| Surface | The words |
|---|---|
| Ledger-wide, unknown | `unparsed count unavailable` — **kept verbatim, test-pinned** |
| Ledger-wide, known | `{n} unparsed in the ledger` |
| Per page | `unparsed count unavailable for this page` / `{n} unparsed on this page` |
| A part that could not be counted | `—`, never `0` |
| Next's set-aside bucket | `status could not be classified` |
| Bottleneck's | `Erik-owned items whose status could not be classified` |
| A defect nobody graded | fuchsia `unparsed` badge + "It cannot trigger FR-79's contested state, so it is stated here rather than dropped." |

The standing clarification under an unknown total: **"Nothing was counted, so this is not a claim
that everything classified."** I changed u3's "statement" to "claim" — a claim is what the product
refuses to make.

### unavailable vs 0

Erik's own words are that suppressing it makes an unknown count look like a clean one. So:
`unavailable` (never read), `not countable` (elapsed with no start), `not recorded` (nobody wrote
it), `unreadable` (stored but would not decrypt), `—` (absent), `never` (a token used zero times).
**Six different absences, six different words.** I found one place using `"recorded"` as the
fallback for a resolved date that would not parse and changed it to `unreadable`, the word the rest
of the product already uses for that exact failure.

### The four evidence scopes (FR-43)

Four rows, side by side, in the arrangement that shows they are four:

- **observed live** — "Somebody watched this behave correctly in the running deployment."
- **observed elsewhere** — "Watched behaving correctly somewhere that is not the deployment — a local run, a preview, a different environment."
- **asserted** — "Stated to be true. Nothing was observed."
- **not verified** — "Explicitly recorded as unchecked. This is a fact, not a gap in the record."

That last sentence is the one that keeps `not_verified` apart from `evidence_scope IS NULL`, which
u4 built as a fifth display state.

### uncovered vs unproven (FR-49)

I rewrote the ending of `uncovered`, which said "it calls for a different thing" and never said
which. Now: **"No passing test names this requirement at all. Unproven needs its test checked; this
needs a test written."** Two states, two different next actions, named.

### billable vs claimed vs contested (FR-50/51/79)

- **open** — "not every acceptance requirement is covered. Nothing to send."
- **claimed** — "Covered only by tests whose certifier executed the work. FR-51: a review request and not an invoice."
- **billable** — "every acceptance requirement is covered by a passing test somebody other than the builder certified."
- **contested** — "Billable, and an open critical defect stands against one of its acceptance requirements. FR-79: flagged, and never presented as clean."

`contested` renders *beside* `billable`, never instead of it. I added `FR-50:` and `FR-47:` prefixes
to the two rows that lacked them so all eight legend entries name their authority — the reader wrote
the spec, and the ref is the fastest index he has.

### covered vs shipped (FR-75)

- **covered** — "FR-47: a passing test proves the requirement. **This says nothing about whether it is deployed.**"
- **shipped** — "A release names the requirement, in the environments listed. FR-75: built and deployed are different claims."
- not shipped — "No release names this requirement. Being covered by a passing test is a different claim and is shown separately."

I also added the guard to Untested's all-clear line: **"Whether any of it is deployed is a separate
question — see Committed."** A clean coverage report is exactly where over-reading happens.

### carried vs closed (FR-30), and the third case

`carried` = "the gap is still owned and still open"; `closed` = "decided against. Not the same as
done." Absent = an em-dash with "No disposition was recorded. That is a gap in the record, not a
decision."

### `wont_fix` vs `verified` (FR-67)

Kept as two badges with two treatments. The three reasons `verified` is withheld are in plain
language rather than enum spelling: "no passing test names this defect" / "no work item is recorded
as fixing it" / "the only passing test was certified by whoever fixed it".

### blocked vs waiting

Blocked's group header reads `{n} blocked · {n} waiting` and the two tables inside are separately
titled **"Blocked work items"** and **"Open external waits"**. Waits' empty state says "Nothing is
waiting on anyone outside the studio", never "nothing is blocked".

**This is where I found a defect.** The work-item filter was labelled **"Waiting on a wait"** —
redundant, and imprecise about the very distinction the product exists to keep. `list.ts:192` shows
it filters `external_wait_id IS NOT NULL`, external waits only, not internal blockers. Relabelled
**"Held by an external wait"**, matching the table's own `external wait` / `blocker` cells. The URL
parameter is still `?blocked=1`; queued rather than renamed.

### owner (FR-52)

Blocked's empty state now carries the reason the grouping exists: "grouped by owner **so Erik's rows
sit apart from a client's or a vendor's**."

### The two regression kinds (FR-69)

Two sections, never one number. Kind two's empty cell said "the coverage was lost another way";
now **"no test is failing — the coverage was lost without one going red"**, which names the actual
mechanism the section note explains.
