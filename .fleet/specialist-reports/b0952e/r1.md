## Q1 — Version matrix and the TS7/baseUrl trap

**typescript is at major 7 (`7.0.2`) on the registry today — TS7 is current, not hypothetical.**
This is confirmed both by today's `npm view` and by a prior fleet run's direct observation
(`Knowledge/TypeScript 7 removed baseUrl outright and no longer auto-includes node_modules
types.md`, run `be343c`, 2026-08-05, confidence high): `"baseUrl": "."` in `tsconfig.json` fails
hard with `TS5102: Option 'baseUrl' has been removed` on `typescript@7.0.2` — not a deprecation
warning, a hard error. **There is no successor option; delete the line, do not replace it.**

**Does the chosen pair resolve path aliases?** Yes, but only because we are pinning **Next 16**,
not Next 15.5. The same vault run chain (`Knowledge/...TypeScript 7 removed baseUrl...md`, updated
2026-08-06 from run `cd414c`) directly observed: Next 15.5 builds its path aliases from tsconfig
`paths` **via `baseUrl`**, so `next@15.5.22` + `typescript@7` fails to even load `next.config.ts`
(`Cannot read properties of undefined (reading 'fileExists')`) and every `@/*` import breaks.
**Next 16.3.0 resolves `paths` alone, with no `baseUrl` involved, and built cleanly.** We are
pinning `next@16.3.1`, above that verified floor, so this combination is expected to work — this
run's pin is consistent with the spec's stated constraint, not in tension with it.

**`tsconfig.json` shape for `u1`'s scaffold:**
```jsonc
{
  "compilerOptions": {
    // no "baseUrl" line — TS7 removed it; the option does not exist to set
    "paths": { "@/*": ["./src/*"] },
    "types": ["node"] // TS7 no longer auto-includes @types/node; set explicitly or
                        // node:fs / process imports fail as if the package weren't installed
    // ...rest per Next 16 defaults
  }
}
```
The `"types": ["node"]` line is a second, independent TS7 break (same vault note): missing Node
globals present as ordinary module-resolution failures (`Cannot find module 'node:fs'`), not as a
config error, and cost a full build cycle to diagnose in the source run. Put both fixes in the
scaffold template up front.

**Tailwind v4 + shadcn/ui CLI: yes, compatible, and it's the default path today.**
Per `ui.shadcn.com/docs/tailwind-v4` (fetched today): "new projects initialize with Tailwind v4 by
default." No `tailwind.config.js` is generated — leave the `tailwind` config field blank/absent in
`components.json`; everything (colors, radius, etc.) lives under `@theme` in the global CSS file
(e.g. `--color-background`, `--color-foreground` as CSS custom properties, not a JS config
object). `tailwindcss-animate` is superseded by `tw-animate-css`.

**Init command** (`ui.shadcn.com/docs/installation/next`, fetched today):
```bash
pnpm dlx shadcn@latest init -t next
# then, per component:
pnpm dlx shadcn@latest add button
```
Package name is **`shadcn`**, not `shadcn-ui` (that name is retired). Requires the `@/*` alias
already present in `tsconfig.json` (satisfied by the `paths` block above) and Tailwind already
installed (`tailwindcss@4.3.3` + `@tailwindcss/postcss@4.3.3` wired into `postcss.config.mjs`
before running init).

## Q2 — pgcrypto + Supabase Vault, current API

**Current Vault API surface — confirmed both by live doc fetch today (`supabase.com/docs/
guides/database/vault`) and by a prior fleet run's direct probe (`Knowledge/pgcrypto plus
Supabase Vault - the working shape...md`, run `cd414c`, 2026-08-06, confidence high, re-verified
live on Postgres 17.6):**

- `vault.create_secret(new_secret text, new_name text default null, new_description text default
  null, new_key_id uuid default null) returns uuid` — confirmed to exist.
- **There is no `vault.get_secret()`.** Reads go only through the view
  `vault.decrypted_secrets` (columns include `id`, `name`, `decrypted_secret`, ...).
- Generate the key inside the database rather than passing one in from the app:
  `vault.create_secret(encode(gen_random_bytes(32),'base64'), 'my_key_name', 'description')`.

**pgcrypto call pair for a text column:**
- Use **`pgp_sym_encrypt(plaintext, key)` / `pgp_sym_decrypt(ciphertext, key)`**, not `encrypt`/
  `decrypt` (those are the lower-level symmetric-cipher pair and require you to manage IVs/padding
  yourself — `pgp_sym_*` is the correct high-level pair for this use case).
- `pgp_sym_encrypt` returns **`bytea`**, not text — armored-text output exists for pasting into
  text contexts and is not needed here. **Declare the column `bytea`.**
- Non-text values cast both ways: `pgp_sym_encrypt(v::text, k)` / `pgp_sym_decrypt(..)::type`.
  `jsonb` round-trips cleanly with no special handling.
- **Known trap, worth carrying into `i1`:** `generate_typescript_types` emits `bytea` columns as
  `string | null`, because PostgREST serializes `bytea` as a `\x`-prefixed hex string — not
  plaintext, not a `Buffer`. Route all reads of encrypted columns through a decrypt RPC so the
  generated TS types match what the UI actually consumes; never read the raw column client-side.

**Extensions and schema:**
- `pgcrypto` — **already installed on a hosted Supabase project, in schema `extensions`, not
  `public`.** Directly observed in the source run; no `CREATE EXTENSION` was needed there. `i1`
  should still guard with `CREATE EXTENSION IF NOT EXISTS pgcrypto WITH SCHEMA extensions;` for
  idempotency, but expect it to be a no-op on a fresh hosted project.
- `supabase_vault` — the `vault` schema and its functions/views were directly usable in the source
  run with no explicit `CREATE EXTENSION` step recorded. Supabase's own docs (fetched today,
  `supabase.com/docs/guides/database/vault`) give the general form for enabling it —
  `CREATE SCHEMA vault; CREATE EXTENSION supabase_vault WITH SCHEMA vault;` — but do not state
  whether a hosted project ships it pre-enabled. **NOT VERIFIED for this specific project — settle
  it in `i1` with `SELECT * FROM pg_extension WHERE extname = 'supabase_vault';` against the
  actual provisioned project before writing migrations that assume either state.** Guard the
  migration with `CREATE EXTENSION IF NOT EXISTS supabase_vault WITH SCHEMA vault;` either way —
  costs nothing if already present.

**`SECURITY DEFINER` wrapper shape** (from the same vault note, directly observed):
```sql
create or replace function app.decrypt_field(ciphertext bytea)
returns text
language sql stable security definer set search_path = ''
as $$
  select pgp_sym_decrypt(
    ciphertext,
    (select decrypted_secret from vault.decrypted_secrets where name = 'app_field_key')
  )
$$;
```
**Make it raise, not return NULL, on a missing key.** The natural implementation silently returns
`NULL` when the `vault.decrypted_secrets` subquery finds nothing (e.g. a renamed secret) — that
reads as absent data, not as a failure, and is silent data loss. Add an explicit `IF ... IS NULL
THEN RAISE EXCEPTION` guard around the key lookup before decrypting.

**Grant/revoke — confirming the standing rule, not re-deriving it:**
```sql
revoke execute on function app.decrypt_field(bytea) from public;
revoke execute on function app.decrypt_field(bytea) from anon;
revoke execute on function app.decrypt_field(bytea) from authenticated;
grant execute on function app.decrypt_field(bytea) to service_role; -- or a narrower role, per §7a
```
Confirmed by the same vault note: PostgREST exposes any function with EXECUTE granted to `anon`/
`authenticated` as a callable RPC — an unrevoked decrypt helper is a public decryption oracle.
`ALTER DEFAULT PRIVILEGES` does not close this; every new function needs the per-name `REVOKE`
above, every time.

## Q3 — MFA (AAL2) enforcement inside RLS

**Confirmed by direct prior-run measurement** (`Knowledge/Enforce MFA in RLS - an app-layer
second factor is not a boundary when the anon key ships in the browser.md`, run `cd414c`,
2026-08-07, confidence high). No contradicting information found in today's research — the JWT
`aal` claim and `auth.jwt()` accessor are Supabase's own stable, documented mechanism and nothing
in this run's checks surfaced a change.

**Claim/accessor:** `auth.jwt() ->> 'aal'`. Value `'aal2'` indicates a second factor was used;
`'aal1'` is first-factor-only. Read it through `coalesce(auth.jwt() ->> 'aal', '') = 'aal2'` so a
token with no `aal` claim at all fails closed rather than erroring or defaulting open.

**Copy-pasteable pattern — a chokepoint helper, not 54 hand-edited policies:**
```sql
create or replace function app.assurance_satisfied() returns boolean
  language sql stable security definer set search_path to ''
as $$ select coalesce(auth.jwt() ->> 'aal', '') = 'aal2' $$;
```
Conjoin this into the small number of `SECURITY DEFINER` helpers policies already route through
(a workspace/tenant resolver, an is-admin predicate) — so the resolver returns `NULL` and the
admin predicate returns `false` when assurance isn't satisfied. Every policy already calling those
helpers inherits the requirement with two edits, not dozens.

**What an anon or aal1 session sees:** with the chokepoint wired, `aal1` reads **0 rows** across
all protected tables (measured: 0 of 15 tables in the source run after the fix, vs 7 of 7 —
including the audit log — before it). Anon (no session at all) sees nothing under `auth.uid()`-
based policies regardless, since it fails at the identity-resolution step, before assurance is
even checked. `aal2` continues to read/write normally.

**Load-bearing near-miss to design around in `i1`, not discover in prod:** a blanket `aal2`
requirement can lock every unenrolled user out of the MFA-enrolment screen itself — the only
screen that gets them to `aal2` — which is unrecoverable for a fresh install and invisible to any
unit test (it only shows up for a never-enrolled user). Whether a carve-out is needed depends on
whether the enrolment path resolves identity through a service-role client (no carve-out needed)
or through the same RLS-gated path (carve-out needed). **This must be measured against the actual
enrolment flow `i1`/`u1` build, not assumed** — clear a test account to zero factors, sign in, and
walk enrolment end to end.

**Prove the chokepoint, don't just trust it:** query for any policy whose `qual`/`with_check`
touches neither helper — if that returns rows, those policies need the predicate added directly.

## Q4 — Per-token rate limiting, no new vendor

Spec forbids adding a vendor. The one directly relevant vault note on this stack
(`Knowledge/Vercel experimentalServices - Upstash KV Pattern.md`) is **not usable as a precedent
here** — it solves ephemeral-instance state with **Upstash**, which is a new paid vendor and out
of scope per FR-8's constraint. Q4 required fresh research; nothing here is carried from that note
except the general shape of "ephemeral compute needs a durable counter somewhere."

**Option A — Postgres-backed counter (via Supabase), no new vendor.**
A single table plus one `SECURITY DEFINER` RPC, called at the top of every ingest/answer handler:
```sql
create table app.rate_limit_counters (
  token_id uuid not null,
  window_start timestamptz not null,
  request_count int not null default 1,
  primary key (token_id, window_start)
);

create or replace function app.check_and_increment_rate_limit(p_token_id uuid, p_limit int, p_window_seconds int)
returns boolean
language plpgsql security definer set search_path = ''
as $$
declare
  v_window timestamptz := date_trunc('second', now()) - (extract(epoch from now())::int % p_window_seconds) * interval '1 second';
  v_count int;
begin
  insert into app.rate_limit_counters (token_id, window_start, request_count)
  values (p_token_id, v_window, 1)
  on conflict (token_id, window_start)
  do update set request_count = app.rate_limit_counters.request_count + 1
  returning request_count into v_count;
  return v_count <= p_limit;
end;
$$;
```
This is a fixed-window counter (simplest correct shape; a sliding window needs two buckets read
together, straightforward to extend later). **Cost:** zero — it's the database already in the
stack. **What it fails at:** every check is a database round-trip on the hot path of every
request (added latency + connection-pool pressure under load); a fixed window has the standard
boundary-burst weakness (2x the nominal limit possible across a window edge); needs a periodic
cleanup job (cron or scheduled Edge Function) to prune old rows or the table grows unbounded.

**Option B — Vercel WAF rate limiting (native, Pro plan).** Fetched today from
`vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting`: this is a firewall-level rule
(dashboard-configured, Fixed Window algorithm on Pro; Token Bucket is Enterprise-only), evaluated
before the request reaches app code. **Decisive limitation for this spec: on the Pro plan, the
only counting keys available are IP and JA4 Digest.** Counting by an arbitrary request header
(e.g. `Authorization: Bearer <token>`) — which is what "per token" requires — is an **Enterprise**
feature only ("User Agent and arbitrary Header keys" is the Enterprise row of the limits table).
**So Vercel's native firewall cannot do per-token rate limiting on Pro as specified.** It could
rate-limit by IP as a coarse outer layer, but that is a different, weaker guarantee than FR-8
asks for and would under- or over-limit any client sharing a NAT/proxy.

**Option C — in-Next.js in-memory limiter (e.g. hand-rolled token bucket in a module-scope Map).**
No new vendor, zero cost. **Fails outright on Vercel serverless**: each invocation may hit a
different, ephemeral instance (the exact failure mode the Upstash vault note documents from a
different but structurally identical Vercel deployment), so the counter doesn't persist across
requests from the same token and the limit is not actually enforced. Not viable given the target
platform (Vercel, per CLAUDE.md's stack requirement) unless every token's traffic is guaranteed
to land on one instance, which Vercel does not guarantee.

**Recommendation: Option A, the Postgres-backed counter RPC.** It is the only option of the three
that (1) introduces no vendor, (2) actually enforces the limit **per token** as FR-8 requires
(not per-IP, not per-instance), and (3) fits the stack already in place (Supabase is provisioned
regardless). The cost is a per-request round-trip, which is small relative to the correctness gap
in B and C, and can be mitigated later (e.g. batching, a `pg_bouncer`-friendly single round trip
via the RPC above, which is already single-round-trip). This is close to forced rather than a
genuine three-way tradeoff, given B is structurally unable to key on token and C is structurally
unable to persist on this platform — so no question is queued for Erik on this one.
