### FR-58, on every screen and in one definition

Two surfaces, one number, read **once per request**:

- the app shell badge (u1's, previously unwired — see below);
- an `UnparsedBreakdown` strip on each of the six screens, showing the same total plus the
  per-table breakdown `unparsedCensus` already returns.

`src/lib/unparsed-census.ts` memoises the read with React `cache()`, so the two cannot disagree
even in principle. It is gated on a role-holding operator at `aal2` — the census runs on the
service-role client, and an anonymous visitor on `/sign-in` must not learn the ledger's shape from
a header badge. **Every failure yields `null`, never `0`**, and the whole thing is wrapped so a
missing `SUPABASE_SERVICE_ROLE_KEY` degrades the badge instead of taking down every route.

A mutation confirming this: rendering an unknown total as `0` turns 2 assertions red; narrowing the
strip by the screen's filters turns 3 red.

## Layout and density decisions Erik has not reviewed

**None of this is approved.** §5a reads `Approved design: NOT YET APPROVED`, and Erik has never seen
these six screens — they rendered as empty states, so there was nothing to review. What *is*
approved (2026-08-19) is the typography, the violet accent confined to chrome, and the 16-token
state scale with fuchsia reserved for `unparsed`. I used those and did not redesign them. Everything
below is mine.

**1. Six screens, one layout grammar.** Filter bar → rejected-filter report → FR-58 strip →
refusal-or-answer. Every screen, same order. The alternative — each answer laid out for its own
shape — reads better per screen and worse across six, and §5a's ten-second glance is a claim about
moving between them.

**2. Blocked is grouped cards; Next, Committed and Bottleneck are flat tables.** FR-52 says
"grouped by owner" so the grouping is structural. The other three are single ranked lists and a
table is the densest honest form. **Untested and Broken are grouped by engagement**, because FR-48
and FR-71 both say "per engagement" and one merged report produces a number true of no client.

**3. Two tables inside each Blocked group, separately labelled.** Work items and waits have
different columns. I first rendered them stacked and unlabelled; **on the running app they read as
one table that had gone wrong**, at both 1440px and 375px. The labels and the divider are the fix,
and the sub-heading is `sticky left-0` so it survives the horizontal scroll.

**4. Committed's per-requirement detail is a native `<details>`, closed by default.** The row's
`3/4 covered · 3/4 shipped` does not say whether the same requirement is missing from both, so the
per-ref breakdown has to exist; putting it inline would triple the row height on the screen that
most needs scanning. `<details>` rather than an accordion because it works before hydration — which
on this branch is sometimes *forever* (see the CSP finding).

**5. Two legends, both `<details>`, and one thing that is deliberately not one.** Committed and
Untested carry closed-by-default legends defining `claimed` vs `billable`, `covered` vs `shipped`,
and FR-43's four evidence scopes side by side — that arrangement is the only one in which a reader
can see the scopes are *four*. The defect-title convention on Broken is **not** behind a
disclosure triangle, because it governs what somebody types into an unencrypted column, and a
convention nobody sees until after they have broken it is not a convention.

**6. Severity borrows two approved hues.** `critical` on `state-blocked`, `major` on
`state-carried`, `minor` neutral, `unparsed` on the reserved fuchsia. Severity is not one of §5a's
five named states, so this is a borrow, not a mapping. Alternative: two new tokens in a palette
Erik has already approved. **Queued (question 4).**

**7. Milestone state and shipped state ride the neutral ladder, not the colour scale.** The scale's
`open`/`fixed` are *defect* states and a milestone that is not yet billable is not defective; giving
`shipped` a coverage colour would be FR-75's collapse expressed in paint. Both are distinguished by
fill, border weight and treatment. A mutation borrowing `state-verified` for shipped goes red.

**8. Row limits of 25/50/100/250/500 on Next and Bottleneck.** Arguably against §5a's ten-second
glance. **Queued (question 7).**

**9. Broken repeats a table header per severity group** — four header rows on a busy engagement.
The cost of FR-71's grouping plus the rule that empty groups still render. **Queued (question 8).**

**10. Free-text engagement and owner filters, not dropdowns.** §7a leaves the owner vocabulary open
and names `external_wait.owner_type` as free text, so a dropdown would invent an enum the database
does not have. A slug matching nothing produces a named notice, not a silent empty answer.

## Best-guess decisions

1. **Wired the shell badge** (3 lines in `layout.tsx`) rather than leaving it permanently
   "unavailable" beside six screens showing the real number. Queued.
2. **A screen reports a bad filter; the endpoint refuses it.** i7's parser throws `400` — correct
   for an agent. A Server Component that threw would render an error page and lose the whole answer
   over one mistyped parameter, so the screen parser collects `rejected` and says so above the
   answer. Same rule, different response, neither pretends the filter applied.
3. **Amounts formatted as major units** with a fixed non-locale format. Queued.
4. **Severity borrows `state-blocked` and `state-carried`** rather than adding tokens to an
   approved palette. Queued.
5. **`covered` uses the `verified` token.** §5a's own word for a firmly derived state, and coverage
   under FR-47 is exactly that. `unproven` and `uncovered` are scale tokens by name already.
6. **The unautomated reason renders as its stored enum member in mono**, not a friendly phrase.
   u4's `UNAUTOMATED_REASON_LABELS` lives in its route's private `_lib`, and importing across
   another route's private folder — or copying the map — would put a second vocabulary beside the
   database's. Flagged as mild duplication for whoever consolidates.
7. **`RejectedFilters` is a new shared component** whose twin is inlined in u4's `work-items/page.tsx`.
   I did not refactor u4's page into it. Mild, deliberate duplication; reported.
8. **A row limit is not a filter.** It changes how much of the answer is shown, not which rows
   qualify, so it never sets `filtered` and never offers a Clear link that clears nothing.
