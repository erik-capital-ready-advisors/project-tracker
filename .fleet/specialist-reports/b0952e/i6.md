## The §7a / FR-24 conflict — read this one

§7a's `engagement` row: *"operator; agent tokens may read **name and slug only**"*, and its
"Contains" column names **repo paths**. i4 implemented that as `AGENT_ENGAGEMENT_COLUMNS`, which
excludes `repo_path`.

FR-24 says the session record carries *"the working directory, **the engagement it resolves to**"*.
Resolving a directory to an engagement requires `repo_path`. Every request to
`POST /api/ingest/session` — including the session hook's — is agent-authenticated.

**Observed, not deduced:** the first run of the route test returned `403 forbidden_table` on
`select("id, slug, repo_path")`.

This is a security boundary, so I did not guess. **I took the restrictive reading:**

- Resolution from an **explicit engagement slug** works (`slug` is on the allowlist).
- Resolution from a **working directory** is unavailable under an agent token. Such a session is
  stored against `unassigned` and queued for one-click attribution — **FR-26's own stated
  behaviour**, so no record is lost and nothing was invented.
- The code asks for `repo_path` first and falls back only on `forbidden_table`. **Adding
  `repo_path` to `AGENT_ENGAGEMENT_COLUMNS` restores full resolution with no other change.**
- The hook can sidestep it entirely with `DELIVERY_LEDGER_ENGAGEMENT`.

Queued as question 1, confidence `low`. **This is the highest-value item in this report.**

### Column encryption — **read back as ciphertext**

```
work_session.summary at rest      CIPHERTEXT  prefix=c30d04070302f248 bytes=112 plaintext_present=false
work_session.summary round trip   OK          decrypts to the original sentence
work_item.description at rest     CIPHERTEXT  prefix=c30d0407030290ce plaintext_present=false
```

The `\xc30d0407` prefix is the PGP packet header. `plaintext_present=false` is a `like '%…%'` test
against the stored bytes for a distinctive word from the plaintext.

The wire form was **measured before any code depended on it**:
`(encrypt_field(x)::text)::bytea = encrypt_field(x)` → `true`, and the JSON form is `"\\xc30d…"`.
Had that not been an identity round trip, the failure would have been a column of silently
corrupted ciphertext discovered only on first read.

## Best-guess decisions

1. **Restrictive reading of §7a vs FR-24.** Did not widen the grant. Queued.
2. **`blocker.owner` changed in `blocked.ts` itself**, not at persistence.
3. **FR-36 moves `blocked` → `pending` only**, and keeps `external_wait_id` as history.

6. **`evidenceScope` defaults to `null`, not `not-verified`.** "Nobody said" and "somebody looked and

8. **Wait resolution is refused a second time** rather than being idempotent — FR-36 exists to record
   *who*, and a second write would overwrite the first name.
9. **`resolvedBy` is not defaulted from the token label** on the agent route. Which credential was
   used and who resolved it are different facts; the audit row carries the first.
10. **No migration, no `database.types.ts` regeneration, no new dependency**, as instructed.
11. **The fake DB lives under `workitems/__fixtures__/`** rather than a shared `server/__fixtures__/`
    path, to avoid a three-way merge conflict.
