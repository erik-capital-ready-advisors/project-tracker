### Contradiction to route back to the vault

**`Knowledge/Next.js 16 + Tailwind v4 Build Gotchas.md`, entry #1, second correction
(2026-08-06, run `cd414c`) is wrong for this stack.** It states:

> **`unrs-resolver` is not a second gate on Next 16.3.0.** … On `next@16.3.0` the tree contains
> only a prebuilt `@next/swc-darwin-arm64`, which carries no build script, so `sharp` is the
> only package that trips the gate.

Observed here, on `next@16.3.1` / `pnpm@11.1.2`, the exact inverse:

```
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: unrs-resolver@1.12.2
```

`sharp` never trips at all; `unrs-resolver` is the only gate. The reason the earlier note is
wrong as a general claim is that it measured `next@16.3.0` **in isolation**. `unrs-resolver`
does not come from Next — `pnpm why` gives the path
`eslint-config-next → eslint-import-resolver-typescript → unrs-resolver`. So the note is
accurate about Next itself and wrong the moment `eslint-config-next` is in the tree, which is
every real Next project. Suggested amendment: scope the claim to "Next alone", and name
`eslint-config-next` as the actual source.

Two further mechanics confirmed from that note, both of which saved time:
- The gate aborts inside `runDepsStatusCheck` in pnpm's own bundle and kills **every** script,
  not just `dev` — observed verbatim in the stack trace.
- pnpm **silently ignores keys it does not recognise.** `ignoredBuiltDependencies:` had no
  effect and pnpm rewrote its `allowBuilds` placeholder back over it. The note's "verify by
  behaviour, not by reading the file" rule is what caught this.

### New finding worth a vault note

**typescript-eslint cannot run on TypeScript 7, and fails at module-load time rather than
degrading.** `@typescript-eslint/parser/dist/index.js` throws
`Error: typescript-eslint does not support TS 7.0.` on `require`, which takes
`eslint-config-next` down with it. There is no subset of rules that avoids it, because ESLint
cannot parse a `.tsx` file at all without a TypeScript parser. Tracking:
typescript-eslint#10940. The documented side-by-side workaround (give the linter the TS 6 API)
**could not be applied**: pnpm 11.1.2 silently ignored `overrides` in both `pnpm-workspace.yaml`
and `package.json` → `pnpm.overrides`, reporting "Already up to date" and writing nothing to
the lockfile, even under `--force`. Resolution: `pnpm lint` runs oxlint. Anyone pinning
TypeScript 7 should plan for no ESLint.

### Design — chosen from 5a's written direction, because nothing is approved

Spec 5a says `Approved design: NOT YET APPROVED`. **There is no approved mockup and nothing
below matches one.** These are my choices, named so Erik reviews a decision rather than
discovers one.

**Type stack.** Geist (interface) and Geist Mono (identifiers), via `next/font/google`.
Identifiers, run ids, requirement refs, durations and dates render through an `ident` utility
carrying `font-variant-numeric: tabular-nums`, per 5a's requirement that they align in columns.

**Accent — violet, and it never encodes state.** Light `#6d28d9`, dark `#a78bfa`. Used only for
focus rings, the active nav item and primary actions. 5a requires the state scale to be
*separate* from the accent, so I enforced that in both directions: **violet appears nowhere in
the state scale, and fuchsia appears nowhere in the chrome.** A violet pixel always means "you
can act on this"; a fuchsia pixel always means "the system could not classify this".

**Neutral ground.** Zinc. Light `#fafafa` / `#18181b`; dark `#09090b` / `#fafafa`.

**Semantic state scale.** Hue carries the family; a second channel — solid fill / outline /
dashed outline — carries confidence. That second channel is what keeps FR-43's four evidence
scopes distinguishable in greyscale and to a colour-blind reader, which hue alone cannot do
across sixteen states.

### Other decisions

- **Built for six answers, not five.** 5a says "five"; CR-001 FR-71/FR-72 added Broken. Six.
- **The unparsed count has three display states, not two.** `unknown` is distinct from `zero`
  and never renders as `0`. Rendering "0 unparsed" is a positive claim that everything
  classified; making that claim without having checked is the exact failure FR-58 exists to
  prevent. The shell currently passes no count, so it reads "unparsed count unavailable" until
  i1/i2 land. Queued as a question.
- **`shadcn init` was run as `init -d --base radix`, not `init -t next` as the brief specified.**
  `-t/--template` scaffolds a whole project and would have overwritten the pinned
  `package.json`. Same outcome, without losing r1's pins.
- **`shadcn init` damaged two things it wrote and I repaired both.** It replaced my violet/zinc
  palette with its greyscale defaults, and it wrote `--font-sans: var(--font-sans)` — the
  circular self-reference that silently drops the font, since Tailwind v4 resolves
  `@theme inline` at parse time. Both restored; the literal font names carry a comment saying
  to check them first after any re-run of `init`.
- **`typedRoutes` left off.** It emits its route union into `.next/types` during a build, so
  `pnpm typecheck` on a cold worktree — how every fleet unit starts — would fail on correct
  hrefs before any build had run.
- **No service-role Supabase client exists.** `server.ts` uses the publishable key plus request
  cookies, so RLS still applies, and it opens with `import "server-only"` so an accidental
  import from a Client Component is a build error rather than a runtime leak. A service-role
  client belongs in the narrow paths that justify it — `api-integrator`'s call, not the
  scaffold's.
- **`.env.example` untouched**, because I introduced no new variable. No real value was written
  to any file, committed or scratch, and no secret was echoed.
- **ESLint removed rather than left broken.** Leaving a hard-failing `pnpm lint` in place would
  poison every downstream unit's verification; leaving a config that silently lints nothing
  would be worse, since a gate that cannot fail has stopped being a gate.
