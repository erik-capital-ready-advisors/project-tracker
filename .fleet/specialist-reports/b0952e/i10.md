## C1 — CRITICAL, fixed and proven through the product's own path

The fix is `grant execute on function app.gates_are_closed_set(jsonb) to service_role;` and
nothing else. No grant to `public`, `anon` or `authenticated` was restored.

**Reproduced before fixing**, twice, in the role the product actually uses:

| Probe | Observed |
|---|---|
| `set local role service_role; select app.gates_are_closed_set('{}'::jsonb)` | `42501 permission denied for function gates_are_closed_set` |
| `POST /api/ingest/run`, real `ingest:write` token, production build | **HTTP 500**, `work_item` 0 → 0, `fleet_run` 0 → 0 |

**Acceptance evidence — same binary, same payload, only the grant changed:**

| Post | Status | `work_item` | `fleet_run` |
|---|---|---|---|
| run `i10p1`, first time | **200** | 0 → **20** | 0 → 1 |
| run `i10p1`, again (FR-22) | 200 | 20 → **20** (held) | 1 → 1 |
| run `i10p2` — **negative control** | 200 | 20 → **40** (rose) | 1 → 2 |

The control is the point: it is the step that exposed qa-reviewer's own false green, and here
it rises, so the "held" reading above is a real idempotency result and not two failures
cancelling. Observed status is **200 on both posts**, not `201`/`200` — the route returns a
plain `apiOk`. Reporting what I saw.

**Two claims verified independently, not taken from qa-reviewer — both CONFIRMED:**

1. A census of every caller-role context in the live database — CHECK constraints
   (`pg_constraint`), column defaults and generated columns (`pg_attrdef`), index expressions
   and predicates (`pg_index`), RLS policies (`pg_policy`) and view bodies (`pg_class`) —
   returns exactly **one** CHECK constraint calling an `app.*` function:
   `fleet_run_gates_closed_set`. The other 23 hits are all RLS policies calling
   `app.is_operator()`, which **is** granted to both `authenticated` and `service_role`.
   No defaults, no generated columns, no index expressions, and **no views exist at all** in
   `public` or `app`.
2. `app.looks_like_secret` is indeed unexecutable by `service_role` and is reached only from
   inside `app.reject_secret_shaped_identifiers()`, which is `SECURITY DEFINER` and attached
   to one trigger. Postgres checks EXECUTE on a trigger function at `CREATE TRIGGER` time, not
   at fire time, so FR-78 keeps working with no grant.

**No second instance of the defect exists.** The full privilege matrix for all 20 functions in
`app` and `public` was read; every ungranted `app.*` function is reachable only through a
`SECURITY DEFINER` wrapper or a trigger.

One incidental observation, **not** a finding against this build: `public.rls_auto_enable()`
is executable by `anon` and `authenticated`. It is Supabase platform-managed, owned by
`postgres`, and returns `event_trigger`, so it cannot be invoked outside its trigger context.
Inert, and not ours to revoke.

### The regression test, and which shape I chose

I chose the **CI-runnable text analyzer** over a live privilege assertion or an ingest
round-trip, because both of those need a service-role key and would therefore be *skipped* in
CI — precisely where a regression would slip through. `tests/migration-grants.ts` is a pure
function over the migration SQL, in the same discipline as the ingest parsers.

It generalises past this instance: it extracts every `app.*`/`public.*` function named in a
CHECK constraint or an RLS policy expression, models grants and revokes in file order
(including that `CREATE OR REPLACE` *preserves* privileges, which Postgres does and a naive
model does not), and reports any function a reaching role cannot execute.

**Proven able to go red**, which is the property the suite was missing:

- 7 synthetic controls, including one that feeds it a header comment discussing the grant in
  prose — the real migration talks about `grant`, `revoke` and the function name for sixty
  lines, and a text check that reads prose as SQL concludes the grant is present.
- Removing my migration and re-running produces:
  `app.gates_are_closed_set unreachable by service_role — CHECK constraint on public.fleet_run (20260819165903_i5_ingest_idempotency_and_gates.sql)`
  It names the defect, the role and the file that introduced it.
- A guard asserting the migration set is non-empty, so deleting `supabase/migrations/` cannot
  make the suite pass.

**This test is not evidence the route works.** It defends against recurrence. The HTTP round
trip above is the acceptance evidence.

## Correction to the follow-up brief: `payload.ts` never rolled its own

The brief stated that `unknown-keys` is imported "by `releases/input.ts` and
`sessions/input.ts` only" and that "`payload.ts` rolls its own". That is not so.
`src/lib/server/ingest/payload.ts` has imported `unknownKeyProblems` through the
`@/lib/api` barrel since `c65e44d`, and there are three callers of one module,
not two callers and a duplicate. Nothing was consolidated because there was
nothing to consolidate.

**The reason the grep said otherwise is itself the finding**, and it is fixed in
`b980e1a`. Four files carried a literal U+0000 byte inside a string or template
literal:

| File | What the NUL is | Author |
|---|---|---|
| `ingest/payload.ts:86` | a NUL-byte filename guard | i5 |
| `ingest/plan.ts:318` | composite-key separator | i5 |
| `qa/persist.ts:204,281,287` | composite-key separator | i7 |
| `workitems/rules.ts:237` | composite-key separator | i6 |

Every intent is correct and none was changed. The defect is writing the byte
**raw** instead of the `\0` escape: `file(1)` reports the file as `data`, and
**`grep` and `git grep` treat it as binary and silently skip it** — not an error,
not a warning, just a shorter result list. All four predate my work; I confirmed
they are present at my parent commit `a88e18f` and introduced none of them.

The cost was real and landed inside this run: a grep returned a short list, a
reviewer concluded a file duplicated a module, and that conclusion was written
into an instruction sent to me. This is the product's own central rule — a silent
default is worse than a failure — appearing in the tooling rather than the data.

Behaviour preservation was proven, not asserted: byte-level, each new file equals
the old with every `0x00` replaced by the two bytes `\` `0` and nothing else,
checked programmatically before writing; semantically, verified in node that
`"\0" === String.fromCharCode(0)` and that `` `${x}\0${y}` `` yields char codes
`70,0,84`. `tests/source-hygiene.test.ts` is the guard, proven red on the pre-fix
tree where it names all four files, and carrying a non-empty-corpus check so a
broken directory walk cannot make it vacuously green.

**This was outside the brief I was given** (waits route, its input module, a
test). I did it because the harm is demonstrated rather than theoretical, and
because the next reviewer's grep would mislead them the same way. It is an
isolated commit and can be dropped on its own.

   a credentialled test is a skipped test in CI.
4. **`unhonouredSlug`/`resolutionDegraded`/`attributionNote` are additive response fields.**
   No existing field changed meaning, so no caller breaks.
5. **Reported HTTP 200 rather than the 201 the dispatcher expected** for the ingest run posts.
   The route returns a plain `apiOk`. I did not change it to 201 — that is a wire contract and
