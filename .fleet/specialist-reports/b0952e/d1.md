## Controls I closed by observation

### 1. HTTP → HTTPS redirect (i4 open item #3) — CLOSED

```
$ curl -sS -D- -o /dev/null http://project-tracker-6bo4qchx6-…vercel.app/
HTTP/1.0 308 Permanent Redirect
Location: https://project-tracker-6bo4qchx6-…vercel.app/
server: Vercel
```

Plain HTTP never serves content. **Caveat recorded honestly:** this 308 is Vercel's *edge*, not the
application's configuration — `HTTP/1.0`, `server: Vercel`, and none of the app's headers. The
control holds on this deployment; it is not a property of the repo and would not survive a move to a
host that does not do this.

### 2. The full security header block over real production TLS (i4 #3, i5 #6) — CLOSED

**The trap I had to get past first.** An unauthenticated `https://` request does *not* reach the
app — Vercel SSO deployment protection answers first:

```
$ curl -sS -D- -o /dev/null https://project-tracker-6bo4qchx6-…vercel.app/
HTTP/2 302
location: https://vercel.com/sso-api?url=…&nonce=…
strict-transport-security: max-age=63072000; includeSubDomains; preload   ← NOTE: preload
x-frame-options: DENY
```

Those are **Vercel's edge headers, not the application's**, and they are close enough to be mistaken
for them. The tell is `preload`: `next.config.ts` documents deliberately *omitting* `preload`, so an
HSTS header carrying it cannot have come from this app. Reporting that 302's headers as the app's
would have been a false green of exactly the kind this run has been catching.

Reaching the app needs `vercel curl`, which the Vercel CLI skill names as the correct alternative to
disabling protection. **Protection was not disabled.** Observed on the app itself:

| Header | Observed value | Present? |
|---|---|---|
| `content-security-policy` | `default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; style-src 'self' 'nonce-…'; img-src 'self' blob: data:; font-src 'self'; connect-src 'self' https://onpvolboecjpdkvurjaf.supabase.co wss://onpvolboecjpdkvurjaf.supabase.co; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests` | **YES** |
| `strict-transport-security` | `max-age=63072000; includeSubDomains` (no `preload`, as intended) | **YES** |

### 3. The CSP nonce is genuinely per-request — CLOSED

Two consecutive requests to `/`:

```
request 1 → 'nonce-PA/xT1LwCG/dx1g0CyaLyA=='
request 2 → 'nonce-sZuR3ifMjCZmpquvDzyNvQ=='
```

Different. A CSP that carried a build-time constant nonce would look identical in a single-request
probe and would be worthless; two requests is what distinguishes them. The nonce also actually
reaches the markup — `/blocked`'s HTML carries `<script nonce="S7t7Ftg8DFSf+2RT/Scdog==">` on every
script tag and on the stylesheet and font preload links, so Next's request-header nonce contract
(documented at length in `proxy.ts`) works on the deployment.

This also settles the WebKit/`upgrade-insecure-requests` concern raised in my brief: over real
HTTPS the directive is a no-op and the scripts are nonce-stamped and served, so the local-http
failure mode does not apply here.

## Best-guess decisions

1. **Copied `.vercel/project.json` instead of running `vercel link`.** `link` offers a project
   choice, and this run forbids selecting a Vercel project. Copying the already-correct ids and
   verifying them against the fixed values passed in my brief makes the selection impossible rather
   than merely careful.
2. **Deployed from the worktree, not from a pushed branch.** A git-triggered deploy would need the
   branch on `origin`, which is the orchestrator's decision, not mine. A CLI deploy carries exactly
   the files at `3c96d40`, which is what needed verifying.
3. **Re-added `APP_ENCRYPTION_KEY_NAME` as Non-sensitive** after Vercel defaulted it to Sensitive. A
   key *name* is not a key, and a write-only value nobody can read back cannot be verified later.
4. **Used `vercel curl` rather than disabling deployment protection**, per the Vercel CLI skill. The
   side effect (a generated bypass token) is queued rather than silently accepted.
5. **Set no Production variable.** `APP_ENCRYPTION_KEY_NAME` is missing on Production and I left it
   missing; production changes need Erik in this run's prompt, and the variable is inert.
6. **Scanned only the `/sign-in` page's chunks** for secret shapes, not every chunk in the build.
   That page instantiates the browser Supabase client, so it is where a leaked key would land. A
   full-build scan would be stronger; this one is bounded and carries a working positive control.
