## What I built

**The contract.** One component, `ProseValue`, exported from `src/components/prose-value.tsx`:

```
data-verify-unit="detail-prose"
data-verify-field   the field's stable name (never its value)
data-verify-state   "present" | "absent" | "unreadable" | "not-requested" | "contradiction"
```

Naming won as follows (full reasoning is in the component's docblock):
- **`detail-prose`** over `prose` (majority — 3 of 5 copies used it; it also matches this
  codebase's existing `detail-*` naming family for detail-view state hooks, `detail-back` /
  `detail-engagement`, where `prose` alone is a name a flat selector could collide with).
- **`data-verify-state`** over `data-verify-prose-state` (the unit name already says this is
  prose; repeating it in the attribute is redundant, and `entity-detail.tsx`'s own
  `entity-identifier` hook already made the same non-prefixed choice for an analogous
  `unreadable` state).
- **`data-verify-field`** kept (4 of 5 copies had it; two of FR-81's eight kinds render more
  than one `Prose` column on the same view, so a selector with no field cannot disambiguate).

**Every state now publishes the attribute — closing the actual defect.** Before this unit,
`/milestones`' `renderProse` returned `undefined` for `absent` and let `DetailField`'s own
generic fallback draw it, which carries no `data-verify-*` attribute at all. `ProseValue`
wraps every state, `absent` included, in the same element — so `[data-verify-unit='detail-prose']`
now finds a slot for every `Prose` field regardless of its state, on every view that has one.

**`absent` renders as `—`, not "not recorded".** Four of five copies already rendered `—` via
the shared `Absent` component (the idiom this product uses everywhere else a value is
genuinely absent: `entity-detail.tsx`'s identity slot, every `DetailField`'s own fallback).
Only `requirements/_components/detail-prose.tsx` rendered the literal string "not recorded".
`—` won.

**`unreadable` is unchanged and unregressed.** All five copies printed the literal word
`unreadable` in `text-state-blocked`; `ProseValue` still does, verified by both the new unit
tests and the migrated per-view tests.

**A defensive fifth branch, not a fifth canonical state.** `ProseState` is a 4-value type
(`present` / `absent` / `unreadable` / `not-requested`), but nothing at runtime stops a caller
from producing `{ state: "present", text: null }` — the two halves of one record
disagreeing. Only `requirements/_components/detail-prose.tsx` guarded against this
(`data-verify-state="contradiction"`); the other three copies would have silently rendered
`<p>{null}</p>` — a blank paragraph under `data-verify-state="present"`, the exact class of
falsehood this whole component exists to refuse. I kept the guard rather than dropping it,
since it strictly improves the three copies that lacked it and costs nothing.

**Call sites are unaffected in prop shape.** `field`, `prose`, `absent` names and values are
identical to what each of the five files already passed; I only renamed the component/import.
`notRequested?` and `className?` (from `detail-prose.tsx`'s original API) are kept on the
merged component for zero-cost compatibility, though no current call site uses either.

## Best-guess decisions

1. **Attribute-name/unit-name contract** (`detail-prose` + `data-verify-state`, dropping
   `data-verify-prose-state` and the alternate `prose` unit name) — explicitly delegated to me
   by the brief ("Pick one ... and document ... why that naming won"). Rationale above and in
   the component docblock. Confidence: high.

2. **`absent` renders `—`** rather than "not recorded" — same delegation. Confidence: high
   (matches 4 of 5 copies and the product-wide `Absent` idiom).

3. **Visual delta from unifying three divergent stylesheets into one JSX tree.** The three
   original contracts did not agree on typography for the same states — e.g. requirements'
   copy applied `max-w-3xl text-xs` to its "unreadable"/"not-requested"/"present" markup that
   the other four did not share, and milestones' "present" text used `max-w-prose` that no one
   else used either. Consolidating to one component necessarily moves *someone's* pixels
   regardless of which naming or wording wins. I kept the plainer, unconstrained-width,
   default-text-size majority treatment (3 of 5: blocker/defect/work-item's existing classes)
   rather than requirements'/open-question's narrower, smaller-text one. Concretely: the
   requirement and open-question detail pages' prose paragraphs may now render slightly wider
   and at the default text size instead of `text-sm`/`max-w-3xl`. This is the one place I
   cannot claim "built as approved with zero visual change" — flagged here per the brief's
   deviation-reporting instruction even though §5a is not itself a mockup this touches (it's a
   design-direction doc, not a rendered screen I have a reference image for). Confidence:
   medium — a reasonable default, but genuinely Erik's call if he wants the narrower treatment
   preserved instead. Not blocking: no `.jsonl` question queued, because the brief explicitly
   assigned this consolidation decision to me and reversing it later (swap which of the two
   className sets `ProseValue` uses) is a one-line change if he prefers the other one.

4. **Default `notRequested` tooltip wording** — kept the 3-of-5 majority's wording ("This view
   did not ask for this field to be decrypted, so nothing here is a statement about what it
   holds.") over `detail-prose.tsx`'s alternate phrasing. No test depends on the exact string;
   pure majority-consistency call. Confidence: high.

5. **`tests/detail-milestone.test.tsx`'s absent-state test was inverted, not just renamed.**
   The old test literally asserted the bug: "`[data-verify-unit='prose']` has length 0" for
   `absent`, with the comment "an absent field borrowed the unreadable marker" as the thing
   being guarded against. That assertion described the pre-B33 defect (no attribute published
   for absent), not a behavior worth preserving. I renamed the test and flipped the assertion
   to check the element **is** found with `data-verify-state="absent"`, and left the
   `contract-milestone-detail` wrapper's own `data-verify-notes-state` assertion untouched
   (that attribute is the milestones page's own, separate contract — out of scope for B33, not
   touched). Confidence: high — this is the one-sentence description of what B33 is.
