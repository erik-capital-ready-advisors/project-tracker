## What I built

1. **Verified QA's recommendation before acting on it.** Read both formatters
   completely. `registry-display.ts:36` does pin `const LOCALE = "en-US";`,
   passed explicitly into every `Intl.NumberFormat(LOCALE, ...)` call in that
   file — so `formatAmount` never consults the ambient/deployment locale the way
   `money-display.ts`'s docstring warns against, and a server render and a
   browser rehydrate call the identical function with the identical hard-coded
   locale string. The hydration-mismatch objection does not apply to the
   survivor. QA's recommendation holds; I did not queue a question against it.

2. **Deleted `money-display.ts`**, moved `MIXED_CURRENCY_TOTAL` into
   `registry-display.ts` (its only consumer, `committed-totals.tsx`, is one of
   mine), and repointed both former `money`-consumers at `formatAmount`.

3. **Resolved the three specific disagreements**, all now flowing through the
   single `formatAmount`:
   - **Symbol vs code** — `formatAmount` wins: `/committed` now renders `$111.00`
     for USD, matching what `/milestones/[id]` already rendered for the same
     amount/currency pair (`tests/detail-milestone.test.tsx` pins that exact
     string; I added a `CommittedTable` test asserting the identical string for
     the identical input, directly exercising the adjacency B32 names as the
     defect).
   - **Thousands separator** — comma, everywhere, via `Intl`; the deleted
     module's U+202F-grouped `"12 500.50"` style is gone. Tested at both the
     table and the totals-strip level.
   - **Currency-code position for an unrecognised currency** — pinned rather
     than redesigned. Measured with `node -e` before writing any assertion
     (see Best-guess decisions): `formatAmount` is itself internally
     inconsistent here, and I pinned both of its paths rather than assuming one.
     Queued as a question since resolving that inconsistency is a design call,
     not something B32 asked for.

4. **`null` handling** — see Best-guess decisions. No live defect: both
   `amountUnreadable` computations (`load.ts:738` for `/committed`,
   `contract-milestone.ts:147` for `/milestones/[id]`) use the identical formula
   (`ciphertext !== null && amount === null`) against the same underlying
   `contract_milestone` row, so the two screens already agreed on which of the
   two null cases applied before this change — the disagreement was only ever in
   how a *readable* amount was formatted, never in the null branching.

## Best-guess decisions

- **Which formatter survived and why:** `formatAmount` (registry-display.ts),
  per QA's recommendation, verified rather than assumed — `LOCALE = "en-US"` is
  pinned and passed explicitly to every `Intl.NumberFormat` call in that module,
  which defuses `money-display.ts`'s stated hydration-mismatch objection
  (that objection is about a formatter consulting the *ambient* locale; a
  hard-coded locale string cannot differ between a server render and a browser
  rehydrate). I did not find the objection still standing, so I did not queue a
  question against the recommendation itself — only against a narrower,
  unrelated inconsistency I found while pinning tests (see Questions queued).
- **What happened to `MIXED_CURRENCY_TOTAL`:** moved into `registry-display.ts`
  unchanged (same string, same export name), since it carries no formatting
  logic of its own to disagree over and its only consumer
  (`committed-totals.tsx`) is one of mine. `registry-display.ts` already has an
  analogous-but-distinct string for the same condition inside `describeTotals`'s
  bare `"not summed"` (used by `totals-panel.tsx`, not mine, not touched) — the
  two are deliberately different lengths for two different layouts, not a
  second disagreement to resolve.
- **What each formatter did with `null` before my change:** `formatAmount(null,
  currency)` returned `{text: "unreadable", readable: false}` unconditionally;
  `money(null, currency)` returned bare `null`. Neither of those `text`/`null`
  values was actually what got rendered for a genuinely-unpriced ("not
  recorded") milestone at either of the two call sites that matter here — both
  `committed-table.tsx` and `milestones/[id]/page.tsx` already re-derived the
  three-way "readable / unreadable / not recorded" distinction themselves by
  checking the separate `milestone.amountUnreadable` boolean, computed
  identically at the two source-data layers (`load.ts:738` and
  `contract-milestone.ts:147`, both `ciphertext !== null && amount === null`).
  So there was no live disagreement on `null` between the two screens — the
  live defect was strictly the formatting of a *readable* number. I preserved
  this exact three-way branch in `committed-table.tsx`, only swapping its
  trigger from `amount === null` to `amount.readable === false`, and added a
  test for the one branch (genuinely unpriced) that the shared fixture never
  exercised.
