## What I built

**The decision named in the brief as the substance of this unit:** where an
open question should be linked from. `@/lib/entity-routes.ts` already reserves
`open_question: "/questions"` as the base path and its own comment says
"`/work-items` and `/waits` already exist as listing screens; the remaining
six base paths are claimed here" -- so the path was already spoken for and the
missing piece was the listing itself. I confirmed independently that none of
the other five entity kinds (`defect`, `blocker`, `requirement`, `release`,
`contract_milestone`) has a list page either (`src/app/{defects,blockers,
requirements,releases,milestones}/page.tsx` all absent) -- `/work-items` and
`/waits` really are the only two precedents, and `open_question` is uniquely
the one B36 calls out as unreachable. I built `/questions` alongside them,
under "Records" in the sidebar (that heading already exists in `main-nav.tsx`
and `command-palette.tsx`, both of which render generically from
`OPERATOR_ROUTES` -- no change needed there).

**The list surface:**
- One row per `open_question`, columns: a navigable reference
  (`run:unit §section`, falling back to `fallbackLabel` when a row carries
  none of the three, exactly as the detail view's own `identityLine` does),
  engagement (client name + slug, linked to `/registry/<slug>`), confidence,
  status, answered-by, answered-at.
- Open by default, `?answered=1` includes answered questions too -- mirrors
  `/waits`' `includeResolved` exactly, same reasoning: an answered question is
  history and stays one click away rather than gone.
- A summary strip states the row count, a per-page "unclassified confidence"
  badge, and a truncation notice when the page is full.
- Three outcomes, not two: a failed read renders `<OperatorLoadNotice>`, a
  successful read with zero rows renders `<EmptyState>` with wording that
  cannot be mistaken for a failure, a successful read with rows renders the
  table. This is the same structure `/waits` and `/work-items` already use.

**No decrypted prose on this screen.** `listOpenQuestions` never selects
`question`, `best_guess` or `answer` -- all three are ciphertext, decryption is
one `decrypt_field` RPC per value, and a list whose job is "which question to
open" has no reason to pay N RPCs per page load for a preview nobody asked
for. `/questions/[id]` already decrypts by default (`withProse` defaults
`true` there) and is one click away.

## Best-guess decisions

1. **Where to link an open question from -- the substance of this unit.**
   Built `/questions` as a listing screen, alongside `/waits` and
   `/work-items`, per the brief's own steer and `entity-routes.ts`'s existing
   reservation of that path. No other candidate surface (the registry, a
   fleet-run view) resolved a real ambiguity, since zero foreign keys
   reference `open_question` and there is nowhere else a reference could
   attach.
2. **`OPERATOR_ROUTES` entry appended at the end, not inserted after
   `/waits`.** Five existing pages index this array **positionally**
   (`OPERATOR_ROUTES[0]` through `[4]`) rather than by looking up their own
   `href`. Inserting after `/waits` would have made my entry index `3`,
   silently pushing `settings/tokens` to `[4]` and `settings/export` to `[5]`
   -- both would then read the wrong `NAV.label`/`NAV.question`/
   `metadata.title`, a regression on a screen this run cannot even view to
   catch (§7c). Appending is the only change to `nav.ts` that cannot do that.
   Queued as question #2 above, since fixing the five call sites properly is
   outside this unit's file ownership.
3. **Confidence rendering: present values plain, `null` loud.** A recorded
   `low | med | high` renders as plain mono text (matching the detail view).
   A `null` -- which per `toConfidence` in
   `src/lib/server/ingest/mapping.ts` means the ingest mapping specifically
   refused to guess a label for an unrecognised wire value (`"medium"`, a
   prose sentence), not merely "nobody filled this in" -- renders with
   `<StateBadge state="unparsed">`, the reserved fuchsia/hatched token,
   following `DefectSeverityChip`'s existing precedent for exactly this shape
   of value. Queued as question #1 above, since it diverges from the
   already-shipped detail view's `<Absent>` treatment for the same value.
4. **No decrypted prose on the list, at all.** `listOpenQuestions` never
   selects `question`, `best_guess` or `answer`. `status` already carries the
   one bit a list needs from that trio, so no boolean stand-in for "has an
   answer" was synthesized either. This keeps the screen at zero
   `decrypt_field` RPCs per page load, matching the brief's steer to "think
   about whether the list needs prose at all."
5. **Sort order: `(status desc, run desc, unit asc)`, not chronological.**
   `open_question` carries no timestamp column at all -- only `answered_at`,
   nullable and set once. There is no way to know which question was queued
   most recently. I ordered open questions first (matching the "open by
   default" framing) with a stable tie-break, and documented the limitation
   in `questions-load.ts` rather than implying an ordering the data cannot
   support.
6. **Default view is open-only, `?answered=1` to include answered.** Mirrors
   `/waits`' `includeResolved` convention exactly, for the same stated reason:
   an answered question is a record worth keeping visible on request rather
   than gone.
7. **`answer`'s baseline-derived classification.** Not rendered at all by this
   list (see decision 4), so this unit introduces no new exposure of it. The
   existing caveat (§7a is silent on `answer`; it is encrypted under the
   security baseline per the migration comment, B13 open) is unchanged by
   this unit's work.
