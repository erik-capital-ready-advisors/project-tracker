## The eight loaders

Each takes the **database uuid** from the route segment. Each returns `null` when no row has that
id — Wave C calls `notFound()` on `null`, matching `src/app/registry/[slug]/page.tsx`. Each throws
`LoadError` when the database **refuses**, which is a different claim and must not be turned into a
404.

```ts
readWorkItemDetail(id: string, withProse = true): Promise<WorkItemDetail | null>
readDefectDetail(id: string, withProse = true): Promise<DefectDetail | null>
readBlockerDetail(id: string, withProse = true): Promise<BlockerDetail | null>
readRequirementDetail(id: string, withProse = true): Promise<RequirementDetail | null>
readOpenQuestionDetail(id: string, withProse = true): Promise<OpenQuestionDetail | null>
readExternalWaitDetail(id: string): Promise<ExternalWaitDetail | null>   // nothing encrypted
readReleaseDetail(id: string): Promise<ReleaseDetail | null>             // nothing encrypted
readContractMilestoneDetail(id: string, withProse = true): Promise<ContractMilestoneDetail | null>
```

All eight call `requireOperator()` **inside**, beside the query. Do not add a gate in the page; do
not remove one either. All eight are wrapped in `cache()`, so a page and its `generateMetadata` pay
for one read — which is why the second argument is a boolean and not an options object.

## The two shapes every view renders

```ts
/** IS `EntityRefItem` — the alias is the definition, not a copy. Pass straight to <EntityRef>. */
type DetailRef = { kind: EntityKind; label: string; id: string | null; title?: string };

/** A §7a-encrypted field, read back. FOUR states; never collapse them to `string | null`. */
type ProseState = "present" | "absent" | "unreadable" | "not-requested";
interface Prose { text: string | null; state: ProseState }
```

**`Prose` needs four branches in the UI, not two.** `absent` = nothing was ever stored.
`unreadable` = ciphertext **was** stored and could not be read back — a fault to show, and
rendering it as blank states "there is nothing here" about a field that was lost. `not-requested` =
you passed `withProse: false`. `<DetailField absent={...}>` covers `absent`; the other two need
their own wording.

## Reference resolution — for the screens (f4, f5)

```ts
interface RefQuery {
  kind: EntityKind;
  ref: string;              // as rendered: `FR-42`, `u4`, `D-7`, `dpl_1`, a wait label, a milestone name
  engagementId: string;
  runId?: string | null;       // work_item only — the fleet_run.id uuid. Supply it if you have it.
  environment?: string | null; // release only
}
type RefResolution = Map<string, string | null>;   // null = resolved to nothing. A finding.

readRefResolution(queries: readonly RefQuery[]): Promise<RefResolution>
readWorkItemRefs(ids: readonly string[]): Promise<Map<string, DetailRef>>

refKey(query: RefQuery): string                             // NEVER build a key by hand
resolvedId(resolution: RefResolution, query: RefQuery): string | null
danglingQueries(resolution, queries): RefQuery[]            // FR-12's count, for a screen that reports it
```

Usage, and it is one round trip per kind for the whole screen:

```tsx
const queries = rows.map((r) => ({ kind: "requirement" as const, ref: r.ref, engagementId: r.engagementId }));
const resolution = await readRefResolution(queries);
// …
<EntityRef kind="requirement" label={q.ref} id={resolvedId(resolution, q)} />
```

**Four rules that will bite if they are not read.**

1. **`id` is the database uuid, never the human ref.** Wave A's note 1, restated: passing `FR-42`
   builds `/requirements/FR-42`, a broken link.
2. **A key is built by `refKey`, never spelled out.** `work_item` carries a run and `release` an
   environment; a hand-written key collides the first time either is supplied.
3. **Resolution refuses when ambiguous.** Exactly one match resolves; zero and two-or-more both
   return `null`. A `u4` with no `runId` resolves only while the engagement holds one `u4`, and
   becomes dangling the day a second run defines one — visibly, which is the intent.
4. **`readRefResolution` decrypts nothing.** Verified: zero `decrypt_field` calls, and no encrypted
   column is even projected. Adopting `<EntityRef>` on a screen costs no RPC.

   engagement slug**". `engagement` is not one of FR-81's eight, so `ENTITY_KINDS` has no entry,
   `entityHref("engagement", …)` returns `null`, and `<EntityRef>` cannot render one.
   **I did not extend the seam**: `tests/m27-gate.test.ts` test 1 asserts `ENTITY_KINDS` equals
   exactly FR-81's eight, and adding a ninth kind turns a passing gate red. The engagement detail
   view already exists at `/registry/[slug]` and is already linked from
   `src/app/registry/_components/engagement-table.tsx:79`, so **every detail loader returns
   `engagement.slug`** and Wave C renders a plain `<Link href={'/registry/' + slug}>`. FR-80 is met
   in substance; the reference is simply not an `<EntityRef>`. Queued as question 3 — Erik's call.

2. **Two migrations disagree about `open_question`'s natural key, and both are recorded.** The
   `20260819144331` table comment says "No natural unique key, deliberately"; `20260819165903`
   added `source_key` and `20260819170622` made its unique index plain. **The brief's premise came
   from the superseded comment.** Resolution by `(engagement_id, source_key)` is therefore
   implemented — and is expected to go unused, which is checkable and was checked:
   `grep -rn "references public.open_question" supabase/migrations/` returns **0**, and
   `grep -rln "open_question\|OpenQuestion" src/app/` returns **0 files**. Nothing points at an open
   question and no screen renders one. It also has no `[id]` route in Wave A's table until f2 builds
   `/questions/[id]`.

3. **`loadRequirementDetail` is the expensive one, deliberately.** It calls `loadCoverageInput`,
   which reads the engagement's whole requirement, work-item, test and test-result set, plus
   `loadShippedIndex`, which reads all of `release_requirement`. That is the cost of the brief's
   binding instruction to reuse `untested.ts` and `shipped.ts` rather than fork FR-47/FR-49/FR-74.
   Correct at this product's size — one operator, tens of engagements, a 31-item reference corpus —
   and stated so it is a known trade rather than a discovery. The alternative was a second
   implementation of the rules, and the first distinction to collapse would have been `unproven`
   versus `uncovered`.

4. **`resolveRefs` reads one whole table per kind per engagement.** Same trade, same reasoning,
   same precedent (`loadShippedIndex` does exactly this and says why). Every read is paged, so it
   is complete rather than silently truncated.

## Best-guess decisions

1. **Resolution refuses when ambiguous, rather than picking the most recent.** Exactly one match or
   `null`. The brief called `null` defensible; I went slightly further and resolve when the match is
   unique even without the run, because that is refusing exactly when ambiguous rather than refusing
   whenever a run is absent — and it keeps `hand`/`external` work items, which have no run at all,
   resolvable.
2. **`refKey` is the only way to build a key**, and its separator is `\0`. The brief specified
   `${engagementId}:${kind}:${ref}`; that shape cannot carry a run or an environment, and two of the
   five parts are free text with spaces in them.
3. **`DetailRef` is an alias of `EntityRefItem`, not a copy.** Type-only import, erased at compile
   time, no runtime dependency from a server module on a component — and no possibility of drift
   across five parallel units.
4. **`Prose` has four states, not two.** `not-requested` in particular is loud on purpose: a screen
   that renders it as blank is stating "there is nothing here" about a field it declined to read.
5. **`withProse` defaults to `true` on the detail loaders** — the inverse of `answers/load.ts`,
   because FR-81 asks for decrypted prose by name. It stays an explicit option, and `resolveRefs`
   never pays it.
6. **`contract_milestone.amount` is decrypted regardless of `withProse`.** FR-54 asks for it by
   name and a milestone view that renders no amount is not one. `notes` follows the flag.
7. **`external_wait` and `release` loaders take no `withProse` at all.** An option that never does
   anything is a promise a later reader will believe.
8. **`open_question.workItem` is an outbound reference.** `run` and `unit` are clear columns whose
   meaning is exactly `(engagement, run, unit)` — the same tuple as
   `work_item_engagement_run_unit_key`. Reading it derives nothing; it is a lookup. Where either
   half is missing or ambiguous it dangles, which `q2` in the fixture exercises.
9. **A failed read throws; a missing row returns `null`.** "The database refused" and "there is no
   such row" are different claims and this product does not collapse them. A 500 and a 404 are the
   right two answers.
10. **`fetchIn` is a nine-line private copy of `answers/load.ts`'s private helper**, rather than
    widening the surface of a module six answers depend on. Stated because it is a duplication and
    should be visible as one; the *paging* underneath it is the single shared `fetchAllRows`.
