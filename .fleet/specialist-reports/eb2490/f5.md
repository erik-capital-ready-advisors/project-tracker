## DEFECT FOUND AND FIXED — the `/work-items` filter round trip

Establishing FR-84's precondition turned up a live defect on the screen the FR-84 gate drives.

`closedSet` in `rules.ts` maps a **wire** spelling to a **stored** one, and `parse` is an exact key
lookup with no normalisation. For two of the six sets the two spellings differ:

| Set | stored | accepted on the wire |
|---|---|---|
| `EVIDENCE_SCOPE` | `observed_live`, `observed_elsewhere`, `not_verified` | `observed-live`, `observed-elsewhere`, `not-verified` |
| `UNAUTOMATED_REASON` | `no_agent_for_stack`, `credential_absent`, `human_judgment`, `client_action`, `out_of_scope` | the hyphenated forms only |

The filter bar's `<option value>` and `withParams` both emitted the **stored** form. Measured, not
inferred — a probe over every option value the bar offers:

```
evidence=observed_live, evidence=observed_elsewhere, evidence=not_verified,
reason=no_agent_for_stack, reason=credential_absent, reason=human_judgment,
reason=client_action, reason=out_of_scope
```

**Eight of the bar's twenty-eight option values were rejected by the screen's own parser.** Selecting
"human judgment" produced the "These filter values were not recognised" banner over an **unfiltered**
list — the exact failure `query.ts`'s header says it exists to prevent, reached from the other end.
And it broke FR-84 outright for those two filters: the URL a detail view restores is only as good as
the parse on the way back in.

Fixed with `toWire`, which `closedSet` already provides for exactly this, applied uniformly to all
six sets in both places. **`rules.ts` was not widened** — teaching `UNAUTOMATED_REASON` to also accept
`human_judgment` would work and is wrong twice: it is not my file, and widening a closed set to make
a stubborn input classify is the failure this project is built around.

**The e2e gate would not have caught this.** `e2e/m27-navigation.spec.ts` drives FR-84 with
`?mode=fleet&status=blocked`, and both of those round-trip fine. A green FR-84 gate was compatible
with two of eight filters being broken.

## Design — spec §5a, and there is NO approved design

`### Approved design: NOT YET APPROVED`. There is no mockup to build to and none to deviate from, so
the section below names what I chose instead, which is what the brief asks for in its place.

**The instruction was to introduce no new design decisions, and I introduced none** — no colour, no
token, no spacing idiom, no re-layout, no CSS change. `src/app/globals.css` is untouched, so
`tests/state-scale.test.ts` reads exactly what it read before and its exception list stays empty.
Fuchsia still means only `unparsed`; the dangling reference is still the outlined `blocked` family,
still not fuchsia, asserted by two tests.

**Three visual consequences of adoption, named rather than left to be noticed:**

1. **`/work-items`' unit column gains the muted reference chip.** It was bare mono text. `<EntityRef>`'s
   known styling is `bg-muted/60 text-foreground/80`, which is byte-for-byte what `<Ref>` in
   `answer-chips.tsx` already draws for `u4` on all six answer screens. This makes `/work-items` match
   the idiom the rest of the product uses, rather than inventing one.
2. **A milestone name and a wait label become monospace.** Both are `<EntityRef>` now, and `ident` is
   part of that component. I passed `className="text-sm font-medium"` so **size and weight are
   unchanged** and only the face moves. Justification: both columns are the natural keys
   `resolveRefs` looks those rows up by (`unique (engagement_id, name)`, `unique (engagement_id, label)`),
   so §5a's "identifiers are monospace" covers them. **This is the judgement call most worth Erik's
   eye** — a milestone name reads more like prose than like an id, and `ident` cannot be merged away
   by `cn` because it is a Tailwind v4 `@utility`, not a class tailwind-merge knows to displace.
   Queued as question 3.
3. **A known acceptance ref changes from an outlined chip to a filled one.** That is the half that is
   *supposed* to change — it is now a link. The **unknown** half is unchanged to the pixel, and that
   is asserted rather than claimed: `ACCEPTANCE_TOKEN` restates this screen's `px-1.5 text-[0.7rem]
   leading-none` over the component's looser defaults, and the test checks the rendered class list
   contains them and does **not** contain `px-1` or `text-xs`. Mutation M2 proves that test is
   red-capable, which also confirmed empirically that tailwind-merge resolves `text-[0.7rem]` over
   `text-xs` rather than my assuming it.

## Best-guess decisions

1. **Fixed the filter round-trip defect rather than only reporting it.** Both files are mine, `toWire`
   exists for exactly this, and the brief's own words — "if you find a filter that is *not* in the URL,
   that is the real FR-84 work" — cover a filter that is in the URL and does not survive it. Queued as
   question 1.
2. **Applied `toWire` to all six closed sets, not just the two that are broken.** Four are no-ops
   today. Applying it only where it currently matters is how this comes back the next time a canonical
   spelling changes.
3. **Kept both `data-verify-known` attributes on an acceptance reference.** They answer different
   questions and the brief said to add the new contract alongside rather than replace it. Added
   `data-verify-unresolved` as the count, so the gap between the two is a number rather than a
   discovery made one token at a time.
4. **`resolved` and `resolvedAcceptance` are optional props defaulting to "nothing resolved".** A
   caller that resolved nothing then dangles everything. Making them required would have broken three
   existing tests, and — more to the point — a caller must not be able to produce a link by omission.
   `unparsed` is the only default, expressed as a prop.
5. **Adopted `<EntityRef>` for the milestone name and the wait label with size and weight preserved.**
   Design consequence 2 above; the one call most worth overruling.
6. **`/work-items` builds its three refs inline with `toRef` rather than taking a resolution map.**
   All three uuids are already in the payload, so a resolution round trip would be a query asking the
   database something the page already knows.
