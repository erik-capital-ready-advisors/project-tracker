## Deviations from the approved design

**No approved design was supplied.** §5a's `Approved design:` line reads **NOT YET APPROVED**, so
there is no mockup to deviate from and no `## Deviations` rows to write. The brief's hard
constraint — introduce no new design decision — was treated as binding, and here is what that
meant in practice, since an unstated default is how every client's product ends up looking the
same:

| Decision | What I used | Where it came from |
|---|---|---|
| Four relationship blocks on one page | `DetailSection` — bordered `section` with a header strip | `EntityDetail`'s own primitive, which is `engagement-coverage.tsx`'s idiom factored out. The brief named that file as the nearest precedent and this is it. |
| Relationship rows | `Table` / `TableRow` inside `overflow-x-auto` | `engagement-coverage.tsx` and `milestone-table.tsx`, unchanged |
| Coverage, shipped, severity, status | `CoverageChip`, `ShippedChip`, `DefectSeverityChip`, `DefectStatusChip` | `answer-chips.tsx`, unchanged |
| Evidence scope | `StateBadge state={scope}` | `state-badge.tsx` — the four scopes are already states on the scale |
| Identifiers, dates, refs | the `ident` mono utility | §5a's tabular-figures rule, already implemented |
| `Prose` state `unreadable` | `text-state-blocked` + `font-semibold`, in mono | **exactly** `milestone-table.tsx`'s treatment for an amount that did not decrypt |
| `Prose` states `absent` / `not-requested` | `text-muted-foreground/70 italic` | `formatIdentifier`'s "not recorded" voice, as `registry/[slug]/page.tsx` draws it |

**No new colour, no new token, no new spacing idiom, and fuchsia is not spent.** An unreadable
field is not an `unparsed` row — it is the opposite failure, a value that was written and cannot be
read back — so it takes the blocked family, which is the distinction `entity-ref.tsx` already
makes for a dangling reference. `tests/state-scale.test.ts` is untouched and its exception list is
still empty.

## Best-guess decisions

1. **All four FR-82 sections render unconditionally, and each empty one states what its emptiness
   means.** An absent section and an empty one are different claims, and on `/untested`'s own
   reasoning the empty one is usually the worse finding — a requirement nothing implements is worse
   than one implemented and untested. The tests assert this against every relationship being empty,
   because that is the case a tidy-looking page silently loses.
2. **The milestone section is `requirement-acceptance`, not `requirement-milestones`**, and carries
   a sentence naming itself as FR-81's inbound side rather than one of FR-82's four. Ruling 4 said
   make the distinction visible to a reader; a `data-verify-unit` alone is not visible to a reader.
3. **Names only from `milestones[]`, never an amount.** i1 projects `id` and `name` and this view
   reaches for nothing else. Asserted: the acceptance section's text is checked to contain no
   currency marker.
4. **A fifth `Prose` branch for the contradiction case.** `state === "present"` with `text === null`
   means the two halves of one record disagree. The repo's rule is to record both rather than pick
   one, so it renders as `read as present, returned nothing` rather than falling through to
   whichever branch is last. Four lines, and it is the product's own ethic rather than
   defensiveness.
5. **`loadForOperator` is used rather than a bare `try`/`catch`.** It is the wrapper every operator
   screen already reads through and it distinguishes four refusal reasons the operator must act on
   differently. It also puts `notFound()` naturally outside the load, because it returns rather than
   throws — so `notFound()`'s own throw cannot be swallowed. The tests mock `getOperatorContext` and
   leave `loadForOperator` real, so the failure path exercises the actual code that keeps "could not
   read" apart from "there is nothing here".
6. **The requirement view's `title` and `identifier` are both `ref`.** A requirement has no name
   other than `FR-nn`. Mildly redundant on screen; `EntityDetail`'s contract says `identifier` is
   the entity's own human reference, and passing it truthfully was worth more than avoiding the
   repetition.
7. **The open question's `title` is `fallbackLabel`, its `identifier` is `run:unit §section`.**
   Ruling 2 and i1's stated intent. `source_key` is a machine key and renders as a field, never as
   a title — no screen in this product asks a person to follow a filename and an ordinal.
8. **Work-item status renders as mono muted text rather than a chip**, to avoid importing from
   another parallel unit's `_components` directory. See the design table above.
9. **`export const dynamic = "force-dynamic"` on both pages**, matching `registry/[slug]/page.tsx`.
   Both read per-request auth, so they are dynamic regardless; stating it makes that explicit rather
   than emergent.
