## Deviations from the approved design

**No approved design was supplied** — spec §5a says `Approved design: NOT YET APPROVED`. So this
section records what changed visually, since "introduce no new design decisions" was the binding
constraint and it is not quite achievable at zero cost.

**No new colour, no new token, no new spacing idiom, no re-layout, no change to
`state-scale`.** `tests/state-scale.test.ts` passes unchanged and its exception list is still
empty. Fuchsia still means exactly `unparsed`; the dangling treatment is `UNKNOWN_REF_TREATMENT`
via `<EntityRef>`, untouched. Wave A's queued hover-underline decision is unchanged.

Three places where the pixels do move, all of them the same change — a token that was styled as
prose becomes the entity-ref chip, because that is what an entity reference looks like in this
product:

1. **`/blocked`, an external wait's label** — was `<span className="font-medium">`, now the chip.
   The chip is `whitespace-nowrap` and a wait label is free text ("App Store review"), so a long
   one will extend the cell; the table is already `overflow-x-auto` and handles it the way it
   handles every other wide identifier.
2. **`/committed`, a milestone's name** — was `text-sm font-medium`, now the chip. This is the
   primary column of the screen, so it is the most visible of the three.
3. **`/next` and `/bottleneck`, the nearest milestone's name** — was `text-foreground text-sm`
   above its due date, now the chip above its due date.

Queued as question 1 with the best guess "use the chip". The alternative — passing each site's old
type treatment through `<EntityRef className>` — preserves the current look and produces chips of
four different sizes across six screens, which is the drift the shared component exists to prevent.

One label string changes, and it is a rule rather than a choice: `/broken` rendered
`item.unit ?? item.id` in two places, printing a bare 36-character uuid for a `hand` or `external`
work item. That is now `fallbackLabel("work_item", id)` → `work item 9c4d5e6f`, per ruling 2. The
href is identical either way.

**Deliberately not changed:** an em-dash `<Absent>` where a *blocked* or *startable* work item has
no unit key. An em-dash is not a reference, so FR-80 does not reach it, and turning every unrecorded
unit key into a link would be a change to what those screens claim. The one place `fallbackLabel`
does replace an absence is `/untested`'s implementer, where FR-55 requires the link and a `hand`
work item is exactly the row that would otherwise lose it.

## Findings

1. **`answers/blocked.ts` collapses a work item's unit key and its uuid into one string, and the
   collapse is invisible at the call site.** `blocksOf` is built as `item.unit ?? item.id`, so
   `wait.blocks` is a `string[]` mixing `u9` with `3f2a1b8c-…`. Asked as work-unit references, the
   uuid entries match no `unit` column and come back `null` — so a `hand` or `external` work item
   held by a wait renders as a reference to nothing while the row plainly exists. I did **not**
   sniff the string for a uuid shape to route around it: deciding which of two meanings a value
   carries is the guess this product refuses, and the failure it would produce is a link to the
   wrong row. `src/lib/server/answers/blocked.ts` is outside this unit's ownership. Queued as
   question 3.

2. **No answer payload carries an `engagementId`, so every text reference costs an extra read.**
   `BlockedItem`, `NextItem`, `CommittedMilestone`, `EngagementCoverage`, `BottleneckItem` and
   `BrokenEngagement` all carry `engagement` as the **slug**; `grep -rn "engagementId"
   src/lib/server/answers/*.ts` outside `load.ts` returns nothing, even though `load.ts`'s internal
   loader types have it and drop it on the way out. `readRefResolution` is keyed by the uuid, so
   four of the six screens now call `listEngagements()` purely to translate. Named as a new read
   below, and queued as question 4.

3. **`Ref` and `RefList` in `src/components/answer-chips.tsx` now have no caller** anywhere in
   `src/` or `tests/` outside that file. Ruling 7 says that conclusion is a finding and not an
   edit, so they are left in place — and `f5` may hold the last callers in a worktree I cannot see.
   Queued as question 6. `answer-chips.tsx` was not opened for writing at any point.

4. **The brief's predicted reset SHA was one commit stale.** Recorded under "Step zero" rather than
   silently absorbed, because a unit that lands on an unexpected SHA and says nothing is
   indistinguishable from one that reset to the wrong ref.

5. **The fleet scratchpad is shared between parallel units, and a sibling overwrote a file I had
   written there.** `…/scratchpad/mutate.py` was replaced mid-run by `f5`'s harness (it names
   `agent-a8e0121c9c6d47b99` and `tests/reference-adoption.test.tsx`). Nothing of mine was lost —
   the mutations had already been applied and reverted — but a unit that read back its own scratch
   file after a sibling wrote one would read the sibling's. Unit-prefixed names from then on.
   Worth a line in the fleet's briefs: the scratchpad is not per-agent.

## Best-guess decisions

1. **`src/lib/answer-screen-refs.ts` exists at all, outside my six trees.** The slug→uuid bridge is
   the same twenty lines on five screens and six copies is six places for it to rot. Kept
   **pure** — no `server-only`, no client, no database — so the six screen components stay
   renderable under vitest in jsdom, which is where FR-83's two states are actually asserted.
   Named after my assigned test file so it cannot collide with another unit's path.
2. **Components take a `RefLookup` function, not a pre-resolved list.** These screens render
   references from inside nested components; threading a parallel `EntityRefItem[]` through them
   means an ordering that has to stay in step with the data it mirrors, and the first thing to
   drift is which reference belongs to which row.
3. **`/bottleneck` got no `refs` prop.** Every reference on it is uuid-backed. A prop that is never
   used is a promise a later reader believes, and an unused resolution round trip is a cost with no
   answer attached.
4. **The engagement read is inside `loadForOperator`, not beside it.** See "Security" above; this
   is the decision that keeps a failed read from rendering as a page of findings.
5. **A reference whose engagement slug this render cannot place is dropped from the batch rather
   than sent with an empty engagement id**, and dangles. `resolveRefs` would filter an empty id out
   of its read anyway; dropping it keeps the batch honest about what was asked.
6. **`<Absent>` is kept where a work item has no unit key on `/blocked`, `/next` and
   `/bottleneck`**, and `fallbackLabel` is used only where a link is required (`/untested`'s FR-55
   implementer) or where a raw uuid was already being printed (`/broken`). An em-dash is not a
   reference, so FR-80 does not reach it.
7. **The engagement slug is a plain `next/link` carrying `data-verify-unit="engagement-link"`.**
   Ruling 3 decided the anchor; the contract attribute is mine, added so qa-reviewer can assert the
   engagement is navigable without an `<EntityRef>` to query. It uses `<EntityRef>`'s own anchor
   classes (`rounded-sm underline-offset-2 hover:underline`) rather than `engagement-table.tsx`'s
   `hover:text-primary`, so no new hover treatment enters these screens.
8. **`tests/answer-screens.test.tsx` renders against a lookup that resolves everything.** Those
   tests check FR-30, FR-49, FR-75 and the rest — distinctions that have nothing to do with
   navigation — and making them dangle would have changed what they exercise. FR-83's two states
   are asserted where they belong, in the new file.
9. **`tests/answer-samples.ts` was not edited.** The two shapes it lacks (a work item with no unit
   key, an implementer with none) are built as local variants in the new test file, so no existing
   test's inputs moved. i1's precedent.
