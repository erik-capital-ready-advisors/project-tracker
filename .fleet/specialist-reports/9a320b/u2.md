## The four things this unit was told were the substance

### 1. "Rendered rather than dumped" — FR-93's `gates`

`RunGates` reads `i1`'s `RenderedGates` and lays out a `<dl>`: gate key left in mono, outcome
right as a chip carrying the stored word (`PASS` / `FAIL` / `NOT_RUN`) in the fleet's own gate
vocabulary, which §5a names as the status language. Three degenerate payloads are stated rather
than swallowed — `malformed` (jsonb permits an array or a scalar), an empty `{}` ("recorded no
gates", explicitly **not** "all gates passed"), and keys whose value is not a string, which are
named because a gate silently dropped reads as one that was never run.

A test asserts there is no `<pre>` in the output and that the section's text contains neither
`{` nor `"build_after_phase1"` — the shape a dump would have. Proven red against a real dump
(mutation 3 below).

### 2. The defects sentence

This is the one the reviewer reads first, so here it is verbatim:

> **which defects this run opened is not recorded**
> Nothing in this ledger records which run opened a defect. The `defect` table carries no run
> column, and the one edge that does exist — a work item named as a defect's fix — says a run
> repaired something, which is a different claim. An empty list here would state that this run
> opened none; nothing checked that, so nothing states it.

Two halves, **two different treatments, deliberately**: `opened` renders as a `Gap` (the product
could not look) while `fixed` renders as `<Absent>` with a stated reason (the product looked at a
modelled edge and found nothing). Giving both the same treatment would erase the only fact the
section has. A test asserts the string `opened no defects` never appears in the section, in
either word order.

No heuristic on `reported_by`, `source_key`, `ref` prefixes or timestamp proximity was used or
considered further than naming it as forbidden.

### 3. `ambiguous` is rendered

`AmbiguousRuns` lists every match with its engagement, branch, mode and row id, chooses none,
and says why it cannot narrow further. **No row links to a run** — there is no route that can
select one, and adding an engagement scope or an `?engagement=` parameter would be building
CR-005 §3.3 (FR-96), which is DRAFT and NOT APPROVED. Each row links to its engagement at
`/registry/<slug>`, which does exist. Tested with two fabricated matches; asserts `notFound()` is
not called and that no `run-detail` shell renders.

### 4. 96 questions and 20 work units on one page

Both listed **exhaustively, with no cap and no "show more"**, and each section states its own
count above the table so completeness is a stated fact rather than an inference from the
scrollbar. Density comes from the row — one line each, mono identifiers, `whitespace-nowrap`
inside tokens — which is §5a's instrument panel applied to ninety-six of something. I considered a
`max-h` scroll container with a sticky header and rejected it: there is no precedent for one on a
content table anywhere in this repository, and it would be a new idiom on a milestone told not to
introduce one.

## Best-guess decisions

Decisions taken under ambiguity, each proceeding on a best guess rather than blocking:

1. **`depends-on` omitted from the work-unit table** rather than substituted. Queued (Q1).
2. **Chips imported across the route boundary** rather than duplicated or hoisted. Queued (Q2).
3. **The ambiguous state links to engagements, not to runs.** No route can select one match, and
   inventing an engagement-scoped key would be building unapproved FR-96. Covered by i1's queued
   routing question; not re-queued.
4. **Question `confidence: null` renders as the reserved `unparsed` badge**, following
   `/questions`' listing rather than `/questions/[id]`'s quieter `<Absent>`. Both exist in this
   repo; a listing follows the listing, for the reason `question-table.tsx` gives — a `null` here
   means the classifier would not guess, not that there is nothing to show. Flagged because it is
   an inherited inconsistency I propagated rather than resolved.
5. **Metadata is the static string `"Fleet run — Delivery Ledger"`**, not `generateMetadata` with
   the run id in the title. `readRunDetail` is `cache()`d so a second read would be free, but
   `/work-items/[id]` and its seven siblings all use a static title and matching them beat a
   marginal improvement to one route.
6. **`section` is rendered but kept out of the state contract.** D4 lists it as a clear column so
   rendering it is sanctioned; keeping ingested text out of `data-verify-*` is one fewer path by
   which an encrypted column could reach an attribute in a later edit, and it costs nothing.
7. **The verdict `unparsed` renders through `StateBadge`.** That is a component call rather than a
   raw string, so it is worth stating that FR-95 is intact: `StateBadge` prints the literal word
   `unparsed` with no label override, and a verdict differing by so much as surrounding whitespace
   is not `=== "unparsed"` and falls through to the byte-for-byte mono text.
