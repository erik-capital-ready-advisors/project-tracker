## 1. How each of the 11 screens reads `searchParams`

**The resolved spec (`.fleet/resolved-spec-d4000f.md:369`) claims "Eleven of these screens already
read `searchParams`". This is FALSE for 2 of 11 as of this HEAD — flagging this loudly per
CLAUDE.md's "record both" rule, because Phase 2 scoping depends on it.**

|---|---|---|

| `/committed` | `src/app/committed/page.tsx:72` | `Promise<SearchParams>` (shared) |
| `/broken` | `src/app/broken/page.tsx:61` | `Promise<SearchParams>` (shared) |

| `/questions` | `src/app/questions/page.tsx:67` | `Promise<Record<string, string \| string[] \| undefined>>` inline (no imported type) |
| `/waits` | `src/app/waits/page.tsx:43` | `Promise<Record<string, string \| string[] \| undefined>>` inline (no imported type) |

**2 of 11 read NO `searchParams` at all today — this is new work for Phase 2, not extension:**

| Screen | File | Evidence |
|---|---|---|
| `/runs` | `src/app/runs/page.tsx` | `grep -n searchParams` returns nothing; the exported function takes no props at all (confirmed by reading the full function signature, lines 1-40 have no params destructure). |
| `/registry` | `src/app/registry/page.tsx:34` | `export default async function RegistryPage()` — zero parameters. |

**The shared type: `SearchParams = Record<string, string | string[] | undefined>` is defined at
`src/lib/answer-query.ts:76`**, and is the type imported by `next`, `committed`, `broken`,
`bottleneck`, `blocked`, `untested` (all `import type { SearchParams } from "@/lib/answer-query"`,
confirmed by grep across all six files). Those six also import a `parse*Query` helper from the
same module (`parseNextQuery`, `parseCommittedQuery`, `parseBrokenQuery`, `parseBottleneckQuery`,
`parseBlockedQuery`, `parseUntestedQuery`, all defined in `src/lib/answer-query.ts:154-241`).

**Divergence 1 — `work-items` duplicates the type instead of importing it.**
`src/app/work-items/_lib/query.ts:94` declares its own
`export type SearchParams = Record<string, string | string[] | undefined>;` — byte-identical shape
to `answer-query.ts:76`, but a separate declaration, and `parseWorkItemQuery`
(`src/app/work-items/_lib/query.ts:154`) is local to that module, not exported from
`answer-query.ts`.

**Divergence 2 — `questions` and `waits` inline the Record type rather than importing anything.**
Neither imports `SearchParams` from `answer-query.ts` or from anywhere; both restate
`Record<string, string | string[] | undefined>` inline in the prop type
(`src/app/questions/page.tsx:67`, `src/app/waits/page.tsx:43`), and both parse ad hoc inline
(e.g. `questions/page.tsx:70-73` does `Array.isArray(params.answered) ? params.answered[0] :
params.answered` directly in the component body — no shared `parse*Query` helper for these two).

**Recommendation for FR-96b (engagement filter param) given this state:** if all four u1-u4 build a
`?engagement=<slug>` reader independently against these three different existing shapes, you will
get three incompatible implementations. Suggest whoever touches `answer-query.ts` first exports one
additional helper (e.g. `engagementFilterFrom(params: SearchParams): string | null`) that all 9
existing-searchParams screens can call, and that `/runs` and `/registry` adopt the same
`SearchParams` type from `answer-query.ts` when they gain `searchParams` for the first time — do
not invent a fourth shape for those two.

(`.fleet/resolved-spec-d4000f.md:352-356`: "a single engagement picker lives in the app shell

## 3. Engagement resolution, archived state, and FR-96c's "no such engagement"

**`/registry/[slug]` resolution:** `src/app/registry/[slug]/page.tsx:62-67` awaits
`params: Promise<{ slug: string }>`, then calls `getEngagement(slug)`
(`src/lib/server/registry/engagements.ts:171-183`), which does
`.from("engagement").select(COLUMNS).eq("slug", slug).maybeSingle()` — no filter on archived state,
so **an archived-not-purged slug resolves today, already satisfying half of the FR-96 requirement
in section "Decided rather than asked" point 2** (`resolved-spec-d4000f.md:370-373`).

**What happens today when a slug resolves to nothing:** `registry/[slug]/page.tsx:136` calls
`if (engagement === null) notFound();` — this is Next's generic 404 page (`notFound()` from
`next/navigation`), **not** a custom "no such engagement" state. FR-96c
(`resolved-spec-d4000f.md:357-361`) requires an **explicit "no such engagement" state with no
rows** for the engagement-filter case specifically — this is a distinct requirement from the
existing `notFound()` behavior on `/registry/[slug]` (which is about a route param, not a query
filter) and should not be conflated with it. Whichever unit builds FR-96c's filter-resolution logic
should build a new explicit state (analogous to the existing `EmptyState` component pattern used
elsewhere, e.g. `registry/page.tsx:74-77`), not reuse `notFound()`.

**Existing "archived" concept — yes, confirmed:** `engagement.archived_at` is a nullable timestamp
column (`src/lib/server/registry/engagements.ts:49` DB row shape, mapped to `archivedAt` at line
68). `registry/[slug]/page.tsx:159` branches on `engagement.archivedAt !== null` to render an
"archived" badge (`data-verify-unit="engagement-archived"`, line 162-164). Server actions already
exist for the full lifecycle: `archiveEngagementSafe`, `restoreEngagementSafe`,
`purgeEngagementSafe` (all imported at `registry/[slug]/page.tsx:20-22`, defined in
`src/app/registry/actions.ts:247-276`).

**FR-96's "picker lists active engagements only" is NOT yet true of `listEngagements()`.**
`src/lib/server/registry/engagements.ts:156-168` — `listEngagements()` selects all rows ordered by
`created_at desc`, **no `archived_at` filter**. The current `/registry` list screen
(`registry/page.tsx:37-79`) renders every engagement including archived ones (the archived badge at
`[slug]/page.tsx:159` exists because engagements it links to can be archived). Whoever builds the
FR-96b shell picker needs a **new** query (or a filter added to `listEngagements`, or a new
`listActiveEngagements`) — do not assume the existing function already excludes archived rows.

## 4. `/registry/new` creation-form pattern (for u2's `/work-items/new`)

- **Page** (`src/app/registry/new/page.tsx`): a thin server component. Reads the operator gate
  (`readOperatorGate()`), renders the form unconditionally (gate panel is advisory above the form,
  not a replacement for it — the page's own comment at lines 15-27 explains this is deliberate: the
  form carries no one's data, so there's nothing to withhold from an unauthorized viewer; the real
  refusal happens server-side on submit).
- **Form component** (`src/app/registry/_components/engagement-form.tsx:3,42-50`): uses React's
  `useActionState(submitEngagement, ...)`, destructured as `[state, formAction, pending]`, and the
  `<form action={formAction}>`.
- **Server action** (`src/app/registry/actions.ts`, `"use server"` at line 1):
  `submitEngagement(previous: RegistryFormState, form: FormData): Promise<RegistryFormState>`
  (lines 133-154). Branches on a hidden `id` field: empty → `createEngagement`, non-empty →
  `updateEngagement`. Validation/parsing happens in a local `engagementFrom(form)` helper before the
  try.
- **Error surfacing:** failures are caught and turned into a user-facing sentence via `refusal(error)`
  (lines 114-123) — `ApiError` messages pass through verbatim (already written for Erik, never a raw
  DB message); an env-misconfiguration `Error` gets a specific sentence; anything else gets a generic
  "nothing was written, try again" sentence, **specifically to avoid leaking a mechanism** for
  unrecognized throws. Returned via `failed(previous, refusal(error))` into the `RegistryFormState`
  the form re-renders from.
- **Redirect on success:** `redirect()` is called **outside** the try/catch, after
  `revalidatePath("/registry")` and `revalidatePath(`/registry/${slug}`)` (lines 151-153) — the
  file's own comment (128-131) explains why: `redirect()` signals by throwing, and catching it
  inside the try would silently swallow a working redirect.

## 5. Work-item row rendering, and where FR-91's planned/STALE badge goes

- **Row rendering:** `src/app/work-items/_components/work-item-table.tsx:165` maps over `items`,
  and line 260 renders `<WorkStatusChip status={item.status} />` per row.
- **`WorkStatusChip`** (`src/app/work-items/_components/chips.tsx:71-91`) is the one place that
  decides how a `StoredWorkStatus` value paints. It is deliberately exhaustive over the stored
  union via `STATUS_CLASS: Record<StoredWorkStatus, string>` (lines 52-63) — every status must have
  an entry or the build breaks (per the file's own comment at lines 48-51). Two statuses
  (`blocked`, `unparsed`) are routed instead through the shared semantic scale,
  `StateBadge`/`WorkState` (`src/components/state-badge.tsx`), via a `SCALE_STATUS` lookup
  (chips.tsx:66-69) — everything else renders on "the neutral ladder" (literal Tailwind classes,
  chosen because Tailwind can't see a runtime-assembled class name, per the file's comment at
  lines 44-51).
- **Where FR-91's planned/STALE state goes:** this chip is used identically by
  `run-work-unit-table.tsx`, `work-item-table.tsx`, and `work-item-detail-view.tsx` (all three
  confirmed via `grep -rln WorkStatusChip src/app/`), so **a new status value added to
  `StoredWorkStatus` (defined in `src/lib/server/workitems/rules.ts` — not opened in this note; u4
  should confirm the exact union member names there) and a new `STATUS_CLASS` entry (or a new
  `SCALE_STATUS` entry if STALE should use the semantic scale rather than the neutral ladder) in
  `chips.tsx` is the one change that reaches every screen that renders a work-item row**, per the
  same "add it once, in the component that owns the scale" pattern the file's own doc comment
  states for `unparsed`/`blocked`. Whether "STALE" is a `StoredWorkStatus` value or an orthogonal
  flag layered on top of an existing status is a decision for u4 to make against
  `rules.ts`'s actual union — **NOT ESTABLISHED here; this note only located the one place the
  rendering decision is made.**

## 6. Test pattern for a fetching screen (StrictMode)

**No shared helper exists.** Every test file that mounts a fetching page inlines the same call:
```tsx
import { StrictMode } from "react";
...
render(<StrictMode>{await RunsPage()}</StrictMode>);   // tests/runs-list.test.tsx:172
render(<StrictMode>{element}</StrictMode>);            // tests/questions-list.test.tsx:80
```
Confirmed by `grep -rln StrictMode src/ tests/` (18 files, including `tests/runs-list.test.tsx`,
`tests/questions-list.test.tsx`, `tests/run-detail.test.tsx`, all `detail-*.test.tsx` files, and
`tests/app-shell.test.tsx`). A search for `renderStrict`/`renderUnderStrict`/`strictRender` across
`src/` and `tests/` returned nothing — **there is no factored-out helper function**; each test file
repeats `render(<StrictMode>{...}</StrictMode>)` with the awaited server-component call inline. New
tests for Phase 2 screens should follow this same inline pattern rather than inventing or hunting
for a helper that does not exist.
